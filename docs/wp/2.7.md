# WP-2.7 — Generation infrastructure + `generate.extend`

- **Spec refs:** [09 §1–3, §4.2, §5, §6, §8](../../specs/09-generation.md), [05 §4, §9](../../specs/05-backend-and-jobs.md), [03 §8.2, §9](../../specs/03-audio-engine.md), [02 §3](../../specs/02-song-model.md)
- **Depends on:** 0.7, 1.10, 2.5 (all Done)
- **Size:** L
- **Branch:** `wp/2.7-generation`

## Goal

Extend a song forward (or backward) with AI-generated audio that matches it. The engine renders
the last 30 s as context, a generation worker asks a model for `bars + 2` bars, `postprocess.py`
conforms and gates the result, the candidates appear in the Audition bar, and the accepted one
becomes a new section whose audio is separated onto the existing stem tracks.

**Acceptance (12):** 09 §9 checks 1 (≥ 2 of 3 extend candidates pass all gates on ≥ 4 of 5 fixture
songs; owner's blind seam listening), 2 (generated audio ends up as stem ribbons on matching tracks)
and 4 (first preview of a 30 s extend ≤ 15 s P50 on a warm GPU). **M2 demo 2** end-to-end.

## Owner decisions

- **Model: ACE-Step 1.5** for extend (its repaint/extend editing; later inpaint/variation in 2.8).
  Bake-off comparisons (MusicGen, Stable Audio) only if ACE-Step fails the gates.
- Develop and measure on the M2 Pro (MPS). **Ask the owner before renting a GPU** for check 4.
  Every timing is labelled "M2 Pro / MPS, not the reference GPU".
- Personal use only; no licence notes in specs or `MODELS.md`.

## What exists

- `services/workers/generate/` is a scaffold (package, packaging test). `bragi_common` provides the
  worker contract (pull, cache, scratch, progress, upload, events); analysis capabilities show the
  pattern (`bragi_analysis/capabilities/*.py`, one module per capability).
- `POST /v1/jobs`, `GET/DELETE /v1/jobs/:id`, the orchestrator and WS event fan-out (Phase 0/1).
  `usage_ledger` table exists with a `credits` column; nothing writes credits yet.
- Engine offline render (WP-1.11): `mixdown` and `stems`; `context` is rejected with a typed error.
- Audition (WP-2.5): `CandidateSource` maps `JobEvent`s to candidate statuses; the Audition bar.
- No seam toolkit (`seam_score`, `loudness_match`, `beat_align`) exists in any language; `match_eq`
  exists as an engine fx (WP-2.3).
- There is no op that adds a `Source`; sources arrive through `analysis.apply`.

## Approach

### A. ACE-Step backend (Python, `services/workers/generate`)

- ACE-Step 1.5 runs as its **own process** with its own uv environment, cloned into the git-ignored
  `.bragi/ace-step/` (`scripts/ace-step-setup.sh`: clone at a pinned commit, `uv sync`, download
  weights into `.bragi/models/ace-step/`), started with its REST API (`acestep-api`, PyTorch/MPS on
  macOS, not vLLM). Our worker talks HTTP to it. This keeps its torch/transformers pins out of our
  uv workspace and makes "hosted API" backends the same shape. Record in **ADR-0015** (generation
  models; ADR-0004 is taken by separation — Q4 now points to ADR-0015).
- `bragi_generate/backend.py`: the `GenerationBackend` protocol of 09 §3.1, `GenRequest`,
  `GenOutput`; `backends/ace_step.py` (extend via ACE-Step's repaint/extend task with the context
  audio, preview tier = fewer steps); `backends/fake.py` (deterministic synthetic audio that follows
  the requested BPM/key, for tests and the live e2e without a model).
- `config/generation_routes.yaml` maps `(capability, tier)` → backend name;
  `services/workers/generate/capabilities.yaml` per 09 §2 (only `generate.extend` implemented).
- `packages/schemas/jobs/capabilities/generate.extend.schema.json` (schema first, then codegen):
  `MusicalContext` (09 §2.1) + `bars`, `direction`, `prompt?`, `tier`, `n`, `seed`.
- `capabilities/extend.py`: resolve the route, call the backend `n` times (progress → `progress`
  events, each finished candidate → a `partial` with its asset), run `postprocess` (task B) and
  regenerate up to 2 rounds for failed gates (09 §6), emit `metrics` (gpuSeconds, model, version).
- Spike first: measure a 30 s extend on the M2 Pro at preview and HQ step counts; record it.

#### A1 spike — ACE-Step 1.5 extend (M2 Pro / MPS, not the reference GPU)

Setup (both scripts are idempotent and live in `scripts/`):

```bash
scripts/ace-step-setup.sh     # clone at ca1e85fe, uv sync, download the weights
scripts/ace-step-serve.sh     # REST API on 127.0.0.1:8001, PID in .bragi/ace-step/serve.pid
```

- Checkout: `.bragi/ace-step` (main checkout), pinned at `ca1e85fe9430179831e6bc6be790c332190a3866`
  (`ace-step` 1.5.0, 2026-08-29). Its own `.venv` is 1.2 GB and stays outside the workers workspace.
- Weights: `.bragi/models/ace-step`, 9.4 GB total — turbo DiT 4.5 GB, 5 Hz LM 1.7B 3.5 GB,
  Qwen3-Embedding-0.6B 1.1 GB, VAE 322 MB. ACE-Step's API hardcodes `<checkout>/checkpoints`, so
  setup symlinks that path at the shared model dir; otherwise the first API start downloads a second
  9.4 GB copy. `ACESTEP_CHECKPOINTS_DIR` alone only covers the CLI downloader.
- Backend: ACE-Step's Apple Silicon tier silently selects native MLX for DiT **and** VAE, and its API
  has no switch for that. `scripts/ace-step-launch.py` flips both flags before importing the app, so
  every number below is PyTorch/MPS (`DiT backend: PyTorch (mps)` in the server log). The 5 Hz LM is
  disabled (`ACESTEP_INIT_LLM=false`): repaint skips it in ACE-Step regardless of `thinking`.
- Cold start: server process to `/health` 4.1 s (models load lazily); `POST /v1/init` (loads DiT, VAE
  and text encoder) 10.5–13.5 s over two starts; first generation after that 21 s. One later run had
  a 114 s VAE decode outlier that did not reproduce; the timings below exclude it.
  **M2 Pro / MPS, not the reference GPU.**

**How to extend.** Use the `repaint` task with `chunk_mask_mode="explicit"`. ACE-Step pads the source
with silence when `repainting_end` is past its end, so the repaint span becomes "last context-overlap
seconds + N new seconds". The spike extended a 30 s context by 30 s with a 2-bar (4 s) overlap:

```jsonc
POST /release_task
{
  "task_type": "repaint",
  "src_audio_path": "/abs/path/context-30s.wav",  // multipart "src_audio" for a remote host
  "repainting_start": 26.0,                        // src_duration - overlap (2 bars = 4 s)
  "repainting_end": 60.0,                          // src_duration + extend_sec
  "chunk_mask_mode": "explicit",
  "repaint_mode": "balanced", "repaint_strength": 0.5,
  "inference_steps": 4,                            // preview; 8 = turbo default (HQ)
  "guidance_scale": 7.0,                           // ignored by turbo
  "prompt": "…", "lyrics": "",                     // empty lyrics = instrumental
  "bpm": 120, "key_scale": "Am", "time_signature": "4",
  "use_random_seed": false, "seed": 1234,
  "batch_size": 1, "audio_format": "wav", "thinking": false
}
```

- Poll `POST /query_result` with `{"task_id_list": ["…"]}`. The outer task can report `status: 1`
  while its inner entry is still `status: 0` with an empty `file`; wait for an entry with `status: 1`
  and a non-empty `file`. Then download `GET /v1/audio?path=…`.
- Result: 48 kHz, stereo, int16 WAV (request `wav32` for float), length `src_duration + extend_sec`
  (60 s for the 30 s spike). The returned file contains the whole timeline: context up to
  `repainting_start`, then the regenerated overlap and new audio. Bragi only uses the tail.
- ACE-Step preserves the audio outside the repaint span exactly (mid-song repaint outside the span:
  residual −80/−56 dB after a global gain), but it **normalises the whole output to −1 dBFS** in the
  HTTP path (the request model has no `enable_normalization`). In the 30 s spike the context was
  scaled by 0.891 on every run (and by 0.89–1.78 on the shorter run), so the postprocess loudness
  match must undo it and the worker must not treat the context as bit-identical.
- **Backward extension works only with client-side pre-padding.** `repainting_start = -N` looks
  supported in the source (left padding) but produced a fully regenerated timeline with no preserved
  context in the spike. Prepending N seconds of silence to the context and repainting `[0, N]`
  preserved the original 30 s (gain 1.78, residual −56 dB) and generated an 8 s intro in A minor.
  A2 should own that mapping.

**Timings** — 30 s context + 30 s new (4 s overlap, 34 s repainted), same caption/BPM/key, three
seeds per tier, warm server. **M2 Pro / MPS, not the reference GPU.**

| Tier | steps | run 1 | run 2 | run 3 | P50 |
|---|---|---|---|---|---|
| preview | 4 | 27.27 s | 27.33 s | 27.41 s | **27.33 s** |
| HQ | 8 | 31.26 s | 30.28 s | 32.39 s | **31.26 s** |

Diffusion is only ~5–6 s at 4 steps and ~8 s at 8 steps; text encoding (~1.5 s) plus the tiled
PyTorch VAE encode/decode (~17–21 s) dominate, which is why doubling the steps costs only ~4 s.
This is above the 15 s preview target of 09 §5, on this Mac and with no offload; a reference GPU is
still needed for check 4. Peak physical footprint of the server was **20 GB** (`footprint`,
`phys_footprint_peak`) against the machine's 21.3 GB MPS tier, while `ps` RSS stayed at 0.8–3.2 GB
because MPS allocations are not process RSS. A 30 s extend is therefore close to the limit here;
longer outputs need CPU offload (the auto threshold is 16 GB, so it stays off at 21.3 GB) or a
larger machine.

**Audio observations** (synthetic 30 s drum+bass+chord loop, 120 BPM, A minor):

- Tempo: 119.68 BPM on every output (0.27 % below the source); the continuation keeps the grid.
- Key: the existing key detector reads the source as C major (relative major of A minor, confidence
  0.15 on this simple loop); all six 30 s outputs were **A minor** (confidence 0.19–0.95). No
  off-key result; the relative-major ambiguity B must allow did not appear here.
- Context: exact outside the repaint span (residual −87…−94 dB) apart from ACE's normalisation gain.
- Seam (500 ms RMS before/after): −8.3 dB on one preview seed (4 steps, seed 1234) and ±1.5 to
  +4.5 dB on the other five — a level step the loudness match in B should remove, with the preview
  dip the kind of candidate the seam gate should reject. No clicks: boundary sample jumps were
  0.00003–0.006, below the local 99th percentile (0.009–0.062).
- Seed: `use_random_seed=false` + `seed` is accepted and echoed in `seed_value`; three seeds gave
  three distinct files. Re-running the same seed and parameters was **not** bit-identical on MPS
  (different SHA-256, same 20.5 s cost on the shorter run), so the HQ re-render "same seed" path (D)
  cannot promise identical audio yet.

### B. `postprocess.py` quality gates (Python, independent of A)

`bragi_generate/postprocess/`: the seven steps of 09 §6 on numpy arrays — sanity, tempo conform
(reuse `bragi_analysis` beat tracking), key check (reuse `bragi_analysis.harmony.key`), beat align
(onset-envelope cross-correlation with the context), splice search in the 2-bar overlap minimising
`seam_score` (spectral flux jump + loudness jump + onset regularity, 03 §8.2), equal-power crossfade
with ±10 ms phase-aware offset, loudness match (short-term LUFS ramps) and a spectral-match result
expressed as `match_eq` parameters. Thresholds in `config/generation_gates.toml`. Returns the
processed audio, every gate's verdict and metric, and `qualityWarning`. Unit tests on synthetic
signals (click tracks at known BPM, tones in known keys, a deliberate seam jump, silence, clipping,
NaN). Deviation to note in 03 §8.2: the seam toolkit lives in the generation worker (Python).

### C. Engine `context` render (Rust + wasm + platform)

Implement `RenderRequest { kind: "context"; range; tracks }` (03 §9): 48 kHz WAV of a tick range,
all tracks or a subset, the range snapped to bar lines by the caller. Native and wasm, a conformance
test, and `EngineHost`/platform plumbing so the app can render, hash and upload it as an asset.

### D. API: submit, credits, warm-up

- `POST /v1/generations/extend` (or `POST /v1/jobs` with capability validation — pick the one that
  matches the existing job route and document it in 05 §2): validates params against the schema,
  checks/records credits (`config/credits.toml`, `usage_ledger` row per job; single-user mode has an
  unlimited daily allowance but still records), enqueues on `jobs.generate.extend.interactive`.
- HQ re-render of an accepted candidate (`tier: "hq"`, same seed) as a background job.
- `POST /v1/generations/warmup`: cheap ping that loads the model in the worker (09 §5).
- Budget guard: daily GPU-seconds cap per environment from config (05 §9).

### E. Model + client: place, separate, map

- Model (schema first): a `source.add` op (`Source { kind: "generated" }` with `Provenance
  { kind: "generation", model, modelVersion, prompt, jobId }`) — or extend an existing op if 02
  already covers it; update 02 §4 and the op catalogue.
- Placement per 09 §4.2 step 4: a new section after the last (or before the first for backward),
  kind guessed (same as last section; `outro` when the prompt asks for an ending), clips on a
  `generated` track. Each candidate is a commit in an audition group (`history.addCandidates`).
- After accept: queue `standard` analysis on the generated asset; when its stems arrive, map them
  onto the existing stem tracks by role (`analysis.apply` with a role → track mapping), and remove
  the mix-only `generated` lane unless separation failed (09 §9 check 2).
- UI: the **extend handle** at the song's end (and start, for an intro) on the canvas (07 §4.x):
  bars (4/8/16), optional prompt, Generate → candidates in the Audition bar with job-status badges
  ("Waiting for a free generator… (~20 s)" from `etaSec`), warm-up ping when the canvas opens.

### E1 design (model shape, placement, stem mapping)

E1 keeps the model change small: one new op plus one optional field, and the existing reconciler
learns about a *placed* source.

- **(a) Adding the generated source — `source.add`.** A new op inserts a `Source`.
  `Source` gains an optional `placement: { sectionId }`: a source with a placement is
  **placement-owned**, not analysis-owned. `source.add` carries the generated
  `Provenance { kind: "generation", model, modelVersion, prompt, jobId, createdAt }`; that is the
  only place a second source enters a document (02 §3.2, §4.2).
- **(b) Placing the candidate — one pure helper, one batch.** `extend_placement` (Rust, exposed as
  `extendPlacement` in model-wasm) is a pure function of the document and the request; it returns
  the candidate's `OpBatch`: `source.add`, `track.add` only when no `generated` track exists,
  `section.insert`, `clip.add`, and for a backward extend a `section.set_transition` on the
  section that now follows the new one. The new section's kind is the last section's kind (the
  first section's for backward), or `outro` when the request asks for an ending; its length is
  the requested number of bars measured at the arrangement edge. The clip's source range starts at
  the candidate's splice offset and its fades use the gate crossfade length. The batch is the
  candidate commit (`history.addCandidates`, 02 §7): source + section + clip are one atomic step.
- **Partial last bar.** Sections are contiguous (`section i` starts at the sum of the lengths
  before it, 02 §3.5), so a forward section begins at the arrangement end. When the context range
  ends on the last full bar before a mid-bar song end, the clip's `srcStart` advances by the
  partial bar's samples, so the new audio continues at the context end and the partial bar plays
  from the previous section (the note's "render the partial bar into the overlap" alternative).
  A backward section is inserted at index 0, which is the context range start (0).
- **(c) Stem mapping — `analysis.apply` for a placed source.** `build_baseline` skips sources with
  a placement, so analysing the generated asset never appends a second end-to-end block, never
  re-times the song, and never creates another full-mix/full-song section. After recording the
  stage, `analysis.apply` reconciles that one placement section from the recorded effect set: if
  a `separation` effect exists, every stem role **and the residual** is mapped onto the first
  track with that role, or onto a new deterministic `trk_…stem:<role>` track, with one
  deterministic `clp_ derive:<sectionId>:<trackId>` clip in the section's lane. The mapping runs
  on every op for that source and is idempotent, so it is the same for any stage arrival order.
- **(d) Removing the mix-only lane.** The same reconciliation removes this source's
  `generated`-role clip from the placement section and drops the lane (and the track, when it
  becomes empty). It does nothing when no `separation` effect is recorded, i.e. when separation
  failed — the generated lane stays and the song is still playable.
- **Determinism and order independence.** Placed sources are excluded from `build_baseline`, so
  the analysis-owned baseline remains a pure function of the unplaced sources and their effects.
  The mapping turns the recorded effect *set* into clips with derived IDs and a role-sorted track
  order; re-delivery and any permutation produce the same document. `section.remove` clears a
  placement that names the removed section and `section.merge` re-points B to A, so a placement
  never dangles (validation also checks this).
- **Undo.** Every step is one history batch: the candidate is one candidate commit, each analysis
  stage of the generated asset is one `system` commit. Undo/redo moves HEAD along stored snapshots
  (02 §7); no inverse ops are needed. A rejected batch leaves the input document untouched, so a
  checkout restores the exact bytes.

## Deviations

- **A1 — PyTorch/MPS needs a launcher.** ACE-Step 1.5's Apple Silicon tier auto-selects native MLX
  for DiT and VAE and its REST API exposes no switch. `scripts/ace-step-launch.py` flips both flags
  before the app starts, so the spike measures PyTorch/MPS as required; the pinned checkout is not
  patched. If ACE-Step later exposes a flag, delete the launcher.
- **A1 — the model dir needs a symlink.** `ACESTEP_CHECKPOINTS_DIR` is honoured by
  `acestep-download` but the API server hardcodes `<checkout>/checkpoints`. Setup points that path at
  `.bragi/models/ace-step` so there is one 9.4 GB copy, not two.
- **A1 — backward extend is client-side.** Negative `repainting_start` is handled by ACE-Step's
  padding code but produced a full regeneration in the spike; prepending silence and repainting
  `[0, N]` preserves the context. The A1 client is forward-only; A2 adds backward and the
  `GenerationBackend` protocol.
- **A1 — seeds are not reproducible on MPS.** The API accepts and echoes a seed and different seeds
  give different audio, but repeating one seed is not bit-identical here. The HQ "same seed" path in
  D must state that, or compare perceptually rather than by hash.
- **C:** the tick -> sample conversion for `context` runs in `bragi-engine` from the
  plan's own tempo map (`tempo_points`/`ppq`), not in the platform adapter. 03 §9 said
  the caller converts a tick range; generation always speaks bars, so the engine owns
  this one. The platform `renderContext(host, doc, range, tracks)` wrapper still takes
  the document, but only to fail fast when the range lies outside the song's total
  `lengthTicks`; the authoritative check (and the typed errors) is Rust.
- **C:** effects are stateful, so `context` renders the effect tail's worth of pre-roll
  before the range and discards it. That is what makes a reverb/delay tail excited
  before the window present *inside* it while the file still ends exactly on the range's
  last sample. Nothing is rendered after the range (no appended tail).
- **C:** the safety limiter is part of the master chain, so it applies to `context` in
  both the "all" and the explicit-track case (a stem is the only render that bypasses it).
- **C:** `bragi_model::bar_aligned_context_range` ties (two ranges equally close to the
  target duration) resolve to the longer range. The helper lives in `bragi-model::time`
  next to the bar/beat math rather than in the engine.

### B — Postprocess quality gates

- **The seam toolkit is Python, in the generation worker.** 03 §8.2 lists `equal_power_crossfade`,
  `loudness_match`, `spectral_match`, `beat_align` and `seam_score` as engine tools, but the only
  v1 caller is the offline gate pass, and it needs `bragi-analysis`'s chroma/key/loudness/onset
  DSP anyway. They live in `bragi_generate.postprocess` (`seam.py`, `match.py`, `alignment.py`,
  `stretch.py`) and 03 §8.2 now says so; a Rust port can use this as the reference when section
  moves need them on the audio thread.
- **Tempo conform warps onto the matched multiple, not onto the literal BPM.** Half and double
  time count as the same tempo (09 §6), so the WSOLA factor is `detected / (requested × m)`: a
  half-time candidate keeps its half-time feel instead of being replayed at double speed, and only
  the residual (≤ 4 %) is corrected. `GateResult.tempo_error` is that residual.
- **Beat positions inside the overlap are the candidate's own tracked beats** (`DspTracker` from
  `bragi-analysis`), not the song's grid: the gate has no tempo map. The tracker can lock to the
  off-beat on a kick+hat pattern; the whole grid then shifts together (the splice is still a
  beat), which the splice test covers.
- **A rejected candidate is still trimmed, crossfaded and loudness-matched.** 09 §6 asks the worker
  to return the best candidate with `qualityWarning` when none pass, so only the splice gate is
  non-fatal; sanity, tempo, key and alignment short-circuit and mark the rest `skipped`.
  `qualityWarning` is spelled `quality_warning` in Python.
- Thresholds and weights are in `config/generation_gates.toml` (repo root, stdlib `tomllib`).
  `bragi-generate` gains `bragi-analysis` as a workspace dependency plus the `numpy`/`scipy` the
  workspace already had; nothing from the `models` group, so the gates run on CPU in CI.

Gate timings (M2 Pro / CPU numpy, not the reference GPU): the whole 58-test suite is 5.7 s; one
8 s candidate through all seven steps is 0.17 s wall clock.

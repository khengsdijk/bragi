# WP-0.5 — Platform shell: web + Tauri boot the same app

- **Spec refs:** [01 §3, §5](../../specs/01-architecture.md) (plus 01 §1, §4, §9, §10;
  [05 §7](../../specs/05-backend-and-jobs.md) for the local DB and migration naming;
  [11 §2](../../specs/11-ux-and-accessibility.md) for copy)
- **Depends on:** 0.1 (Done)
- **Size:** M
- **Branch:** `wp/0.5-platform-shell`

## Goal

One React bundle that boots in the browser and inside the Tauri webview, with every platform
difference behind `packages/platform` interfaces, and a local database + blob cache that persist
across reloads on both.

**Acceptance (from [12](../../specs/12-roadmap.md)):**
1. The same e2e test (create a dummy project, store it, reload, read it back) passes in Chromium,
   Firefox, Safari (web) and in Tauri on macOS, Windows and Linux.
2. `crossOriginIsolated === true` on web.

## Approach

### One bundle, two hosts

`apps/web` is the only Vite entry. Its build output (`apps/web/dist`) is what the browser gets
**and** what Tauri loads (`frontendDist: ../../web/dist`, `devUrl` = the web dev server), so
"the same bundle" is literal, not "the same source". The platform is chosen at runtime in
`@bragi/platform/auto` (Tauri's injected IPC global present → Tauri adapters, otherwise web
adapters); each adapter set is a lazy chunk, so the browser never executes Tauri code and the
desktop never loads sqlite-wasm. The production build confirms it: `dist/assets/tauri-*.js` is a
1.7 kB chunk and `dist/assets/storage.worker-*.js` (sqlite-wasm) is only fetched by the browser
path.

`packages/app` receives a `Platform` object and never knows which one it is. It imports only types
from `@bragi/platform` and nothing from `@tauri-apps/*` — enforced by a Biome
`noRestrictedImports` override on `packages/app/**` plus a unit test over its `package.json` and
sources.

### `packages/platform`

| Interface | Web | Tauri | Fake (tests) |
|---|---|---|---|
| `LocalDB` (`query`, `run`, `transaction`, `close`) | official `@sqlite.org/sqlite-wasm` 3.53.4, opfs-sahpool VFS, in a dedicated module Worker | Tauri commands → `rusqlite` 0.40 (bundled SQLite) | `node:sqlite` in memory |
| `BlobCache` (`put` → `sha256:<hex>`, `get`, `has`, `delete`) | OPFS directory, written through sync access handles in the same Worker | Tauri commands → files under `<data dir>/blobs`, raw request/response bodies | `Map` |
| `FileAccess` (`pickFiles`) | `<input type=file>` | same `<input>` in the webview (native dialogs + watched folders deferred) | scripted |
| Migrations | one TS runner (`runMigrations`) over `LocalDB`; the desktop runs the same SQL through rusqlite with the same `schema_migrations` bookkeeping | | |

`LocalDB` is deliberately SQL-shaped (statement + positional params, rows as plain objects) so the
SQL in `packages/schemas/sqlite/migrations/NNN_name.sql` (05 §7) and every query is shared
verbatim. `transaction(steps)` is the only atomic unit — it runs entirely on the DB side (worker or
Rust), never as `BEGIN`/`COMMIT` spread across IPC round-trips.

A **shared contract suite** (`src/__tests__/contract/*.ts`) runs against every implementation that
can run under Vitest/Node: the `node:sqlite` fake, the sqlite-wasm engine core (on the in-memory
VFS), the worker protocol over a real `MessageChannel`, and the Tauri adapters wired to an `invoke`
double. The Rust side has its own tests (`cargo test`) for the same behaviours through
`rusqlite`, including applying every shared migration file. OPFS itself only exists in browsers, so
it is covered by the e2e, not by Vitest (the bundling of the migrations *is* unit-tested in
`apps/web/src/__tests__/migrations.test.ts`, which compares the bundled glob byte-for-byte with the
directory).

### `packages/app`

React 19 + TanStack Router, code-based routes (no codegen plugin): `/` (projects list + "New
project"), `/song/$id` (reads the project back from LocalDB and checks its blob), `/universe` and
`/fuse` (placeholders). Strings come from `src/i18n/en.json` through a typed `t()`; `@bragi/app`
also exposes `./i18n` so the e2e drivers assert against the app's own copy instead of literals.

The router uses a **hash history**. The same bundle is served from a static host in the browser and
from Tauri's asset protocol on the desktop, and only the hash guarantees that `#/song/prj_…`
survives a reload in both without a server rewrite rule — which was the "SPA fallback" spec gap
below. The CDN configuration (01 §9) can add path routing later without touching the app.

The "dummy project" is a `projects` row (columns mirror 05 §5 minus `user_id`) plus one small blob
in the BlobCache: a canonical, versioned JSON *card* whose SHA-256 is its name. `createProject`
stores the card **before** the row, so a project row without its card cannot come out of it, and
`verifyProjectCard` is a real check that the two still agree — that is what the reload asserts.

### `apps/web`

Vite 8 with COOP `same-origin`, COEP `require-corp`, a strict CSP and `nosniff`/`no-referrer` on
**both** `server` and `preview`; the header set is one exported, unit-tested module
(`src/headers.ts`) that the future deploy WP can consume. The CSP allows `'wasm-unsafe-eval'` (not
`'unsafe-eval'`) and nothing remote; dev adds `'unsafe-inline'` for the `<style>` elements Vite
injects and `ws:`/`wss:` for its HMR websocket, and the production policy has neither.
`optimizeDeps.exclude` for `@sqlite.org/sqlite-wasm` is what keeps `sqlite3.wasm` locatable, and
the emitted build contains the wasm as a hashed asset. The dev server is pinned to `127.0.0.1` so
the e2e polls the address that was actually bound (`localhost` can be `::1` only).

### `apps/desktop`

Tauri 2.12. `src-tauri` joins the Cargo workspace (so clippy `-D warnings` and the workspace lints
apply and there is one `Cargo.lock`), is native-only, and is not part of `build:wasm`.
Commands: `db_query`, `db_run`, `db_transaction`, `blob_put`, `blob_get`, `blob_has`,
`blob_delete`. `build.rs` declares them through `AppManifest::commands`, which is what puts them in
the ACL: from then on **every** command needs an explicit `allow-…` grant, and a command added
without one is denied at runtime instead of quietly reachable (01 §10). The `default` capability
grants the core defaults plus exactly those seven commands to the `main` window — no plugin, no
filesystem scope, no `pickFiles` plumbing beyond the webview's own file input.

Two things about the window are deliberate:

- **The window is created in Rust**, not in `tauri.conf.json` (`"windows": []`), so the harness can
  open a window whose label is not `main`.
- **`custom-protocol` is a default feature.** `tauri::is_dev()` is true whenever the `tauri` crate
  is compiled without it, and a dev build points the webview at `build.devUrl` instead of the
  embedded bundle. Without the feature, `cargo build` produces a binary that silently looks for a
  dev server; the harness runs the real bundle, so the feature must be on.

### Tauri e2e on macOS — what is actually possible

`tauri-driver` (WebDriver) supports Linux and Windows only; WKWebView has no WebDriver. So the
acceptance scenario is written **once** against a tiny `Driver` interface
(`apps/web/e2e/scenario.ts`) and run by two drivers:

- **Playwright driver** — Chromium, Firefox and Playwright WebKit, against both the dev server and
  `vite preview` of the production build (six projects, one test).
- **In-page DOM driver** (`apps/web/e2e/dom-driver.ts`) — compiled to one IIFE
  (`vite build --config e2e/selftest.vite.config.ts`, global `BragiSelftest`) and evaluated in the
  Tauri webview by a `selftest` cargo feature. It drives the real UI through the DOM (controls by
  visible text, fields by their label, React satisfied through the native value setter), reports
  through a `selftest_report` command that only the harness capability grants, and the process
  exits 0/1. `pnpm test:e2e:desktop` (`apps/desktop/scripts/selftest.mjs`) builds the production
  bundle, builds the driver, builds the app with the feature, runs phase *create*, then
  **relaunches the process** and runs phase *read back* against the same data directory — a
  throwaway temp directory (`BRAGI_DATA_DIR`), so real user data is never touched.

What this proves on macOS: the shipped web bundle boots in WKWebView, the Tauri adapters are
selected, the shared migrations apply through rusqlite, and a project and its blob survive a full
process restart and are read back through the UI. What it does not prove: real OS input events (the
DOM driver uses `click()`/`input` events, not OS events), and anything on Windows or Linux.

## Decisions and deviations from the plan

1. **Hash routing** instead of path routing — see the router note above. This resolves the SPA
   fallback gap rather than deferring it to the CDN WP.
2. **App commands are ACL'd.** The plan said "every command is declared in the app manifest
   (build.rs), so each needs an explicit permission"; that turns out to be a choice Tauri leaves
   open (`AppManifest::commands` is optional, and without it app commands are allowed from local
   origins). It is taken here, because 01 §10 asks for allow-listing per command.
3. **The harness window is a different label** (`selftest`) from the shipped window (`main`), with
   its own capability. In a normal build no window has that label, so the grant matches nothing.
4. **The `selftest` build must keep `custom-protocol`** (see above) — a real trap: `cargo build`
   without it produces a binary that tries to reach a dev server.
5. **Playwright WebKit needs a persistent context.** In an ephemeral (private-browsing-like)
   session WebKit refuses OPFS to workers — `navigator.storage.getDirectory()` throws
   `UnknownError` in the worker, which is where sqlite-wasm lives. The WebKit projects therefore
   use `launchPersistentContext`, and the suite builds its own contexts for all engines so the
   browser matrix stays one test. Traces are the price (the runner's trace/video hooks are tied to
   its own context fixture); the driver's transcript goes to the console instead.
6. **The web suite clears the app's storage before each run** (`e2e/reset-storage.ts`). Neither a
   fresh context nor a fresh profile directory is a clean *app* data directory: WebKit keeps
   website data in `~/Library/WebKit/<browser id>/WebsiteData` regardless of the profile path it is
   given, so a previous run's database would still be there.
7. **`@bragi/platform/tauri` exports `createTauriIpc()`.** The harness driver has to reach
   `selftest_report`; exporting the raw IPC keeps `@tauri-apps/*` imported in exactly one place.
8. **`packages/app` has an `./i18n` subpath export** so the e2e drivers look up the labels the app
   actually renders; a renamed label then fails the scenario instead of passing against a stale
   literal.
9. **`tsconfig.test.json` gained `lib: DOM` and `jsx`.** It typechecks `packages/*/src/**/*`,
   including browser-facing sources and their tests, so it needs what those packages build with.
   `apps/web` got its own non-composite `tsconfig.json` (typechecked by `tsc --noEmit` inside its
   `build` script) because it is not a referenced project.
10. **`vitest.config.ts` in `apps/web`** scopes Vitest to `src/**` so it never collects the
    Playwright spec.
11. **Turbo `test` inputs include `vitest.config.ts`**, so a config change invalidates the cache.
12. **`BRAGI_DATA_DIR`** overrides the app's data directory. It exists for the harness; nothing else
    sets it.
13. **`db_run` returns `{ changes }`** rather than a bare number, matching the TypeScript `RunResult`
    the contract suite asserts.
14. **`db_transaction` accepts a script step** (no `params` → `execute_batch`, several `;`-separated
    statements). One shared migration file depends on it, and a Rust test pins the atomicity of the
    whole step, including that `execute_batch` does not commit the surrounding transaction.
15. **The migration checksum is asserted from both languages** with the same literal
    (`sha256:c695…` in `packages/platform`'s test and in
    `apps/desktop/src-tauri/src/migrations.rs`), so the two runners cannot drift on how they hash a
    file.

No new dependency beyond what 01 §1 already names: Tauri 2 + rusqlite + sqlite-wasm + Vite +
React 19 + TanStack Router, all of which are the spec's own choices. `sha2` is the one crate added
behind the scenes for blob hashing (RustCrypto, Apache-2.0/MIT) — a utility, not a framework, so no
ADR is required.

## Spec gaps found

- **CSP vs. Tauri.** A `<meta>` CSP in `index.html` would also apply inside Tauri and block its IPC,
  so the web CSP is sent as a header (Vite `server`/`preview` headers) and Tauri's comes from
  `tauri.conf.json`. Production hosting must send the same headers — the CDN config does not exist
  yet (01 §9), so the header set is one exported module the future deploy WP can consume.
- **SPA fallback.** Resolved by using hash routing (above); if a later WP wants path URLs, the CDN
  and Tauri's asset resolver both need a rewrite rule.
- **Tauri's IPC and the dev server's CSP.** Under `tauri dev` the webview logs
  `IPC custom protocol failed, Tauri will now use the postMessage interface instead`: the page is
  served by Vite with the *web* CSP from `src/headers.ts`, which does not list an `ipc:` scheme, so
  Tauri's first IPC attempt is blocked and its own postMessage fallback takes over. The shipped
  build serves the page from Tauri's asset protocol with the CSP from `tauri.conf.json`, which does
  list `ipc: http://ipc.localhost` (and which Tauri augments itself), and the desktop e2e — the
  production build, both launches — drives every command and the report through it. Worth knowing
  before someone "fixes" the web header set by adding an `ipc:` source that browsers do not use.
- **`isTauriHost` and strict CSP.** The check is `"__TAURI_INTERNALS__" in globalThis`, which is what
  Tauri 2 injects before any page script. If Tauri ever changes that global, `auto.ts` starts
  choosing the web adapters inside the webview — the desktop e2e is what catches it, which is why
  the harness must keep running.
- **Windows and Linux desktop builds are unverified** (Q11). The `desktop-e2e-*` jobs exist for the
  day they can be run.
- **Playwright WebKit is not Safari.** Recorded in Q11 as well; a Safari pass needs a machine with
  Safari (or a Safari-capable CI service).
- **`FileAccess` is the floor, not the goal.** Native folder picking and watched folders (01 §3)
  are library-import work; the interface and the `<input>` implementation are here, `pickFiles` is
  the only method, and `LocalDB`/`BlobCache` name their files the same way on both hosts so the
  later import path does not have to care which host it is on.

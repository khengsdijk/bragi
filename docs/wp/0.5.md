# WP-0.5 — Platform shell: web + Tauri boot the same app

- **Spec refs:** [01 §3, §5](../../specs/01-architecture.md) (plus 01 §1, §4, §9, §10;
  [05 §7](../../specs/05-backend-and-jobs.md) for the local DB and migration naming;
  [11 §2](../../specs/11-ux-and-accessibility.md) for copy)
- **Depends on:** 0.1 (Done)
- **Size:** M
- **Branch:** `wp/0.5-platform-shell`

## Goal

One React bundle that boots in the browser and inside the Tauri webview, with every platform
difference behind `packages/platform` interfaces, and a local database + blob cache that persist
across reloads on both.

**Acceptance (from [12](../../specs/12-roadmap.md)):**
1. The same e2e test (create a dummy project, store it, reload, read it back) passes in Chromium,
   Firefox, Safari (web) and in Tauri on macOS, Windows and Linux.
2. `crossOriginIsolated === true` on web.

## Approach

### One bundle, two hosts

`apps/web` is the only Vite entry. Its build output (`apps/web/dist`) is what the browser gets
**and** what Tauri loads (`frontendDist: ../../web/dist`, `devUrl` = the web dev server), so
"the same bundle" is literal, not "the same source". The platform is chosen at runtime in
`@bragi/platform/auto` (Tauri's injected IPC global present → Tauri adapters, otherwise web
adapters); each adapter set is a lazy chunk, so the browser never executes Tauri code and the
desktop never loads sqlite-wasm.

`packages/app` receives a `Platform` object and never knows which one it is. It imports only
types from `@bragi/platform` and nothing from `@tauri-apps/*` — enforced by a Biome
`noRestrictedImports` override on `packages/app/**` plus a unit test over its `package.json` and
sources.

### `packages/platform`

| Interface | Web | Tauri | Fake (tests) |
|---|---|---|---|
| `LocalDB` (`query`, `run`, `transaction`, `close`) | official `@sqlite.org/sqlite-wasm`, OPFS VFS, in a dedicated module Worker | Tauri commands → `rusqlite` (bundled SQLite) | `node:sqlite` in memory |
| `BlobCache` (`put` → `sha256:<hex>`, `get`, `has`, `delete`) | OPFS directory, written through sync access handles in the same Worker (Safari has no main-thread `createWritable`) | Tauri commands → files under the app data dir, binary IPC bodies | `Map` |
| `FileAccess` (`pickFiles`) | `<input type=file>` | same `<input>` in the webview (native dialogs + watched folders deferred, see below) | scripted |
| Migrations | one TS runner (`runMigrations`) over `LocalDB`, so both platforms apply identical SQL with identical bookkeeping | | |

`LocalDB` is deliberately SQL-shaped (statement + positional params, rows as plain objects) so the
SQL in `packages/schemas/sqlite/migrations/NNN_name.sql` (05 §7) and every query is shared
verbatim. `transaction(steps)` is the only atomic unit — it runs entirely on the DB side (worker
or Rust), never as `BEGIN`/`COMMIT` spread across IPC round-trips.

A **shared contract suite** (`src/__tests__/contract/*.ts`) runs against every implementation
that can run under Vitest/Node: the `node:sqlite` fake, the sqlite-wasm engine core (the same
module the worker uses, on the in-memory VFS), and the Tauri adapters wired to an `invoke`
double. The Rust side has its own tests for the same behaviours (`cargo test`), including
applying every shared migration file through rusqlite. OPFS itself only exists in browsers, so
it is covered by the e2e, not by Vitest.

### `packages/app`

React 19 + TanStack Router (code-based routes, no codegen plugin): `/` (projects list +
"New project"), `/song/$id` (reads the project back from LocalDB and checks its blob),
`/universe`, `/fuse` (placeholders). Strings come from `src/i18n/en.json` through a typed `t()`.
The "dummy project" is a `projects` row (columns mirror 05 §5 minus `user_id`) plus one small
blob in the BlobCache; no song document is created (that needs `bragi-model` ops, WP-0.3).

### `apps/web`

Vite config with COOP `same-origin`, COEP `require-corp` and a strict CSP on both `server` and
`preview` (one module defines the headers; unit-tested). The CSP allows `'wasm-unsafe-eval'` for
sqlite-wasm and nothing remote. Dev additionally allows the HMR websocket and inline styles
(Vite injects CSS as `<style>` in dev only).

### `apps/desktop`

Tauri 2. `src-tauri` joins the Cargo workspace (so clippy `-D warnings` and the workspace lints
apply and there is one `Cargo.lock`), but is native-only and is **not** part of `build:wasm`.
Commands: `db_query`, `db_run`, `db_transaction`, `blob_put`, `blob_get`, `blob_has`,
`blob_delete`. Every command is declared in the app manifest (`build.rs`), so each needs an
explicit permission, and the `default` capability grants exactly these to the `main` window —
no plugin permissions, no filesystem scope. Strict CSP in `tauri.conf.json`.

### Tauri e2e on macOS — what is actually possible

`tauri-driver` (WebDriver) supports Linux and Windows only; WKWebView has no WebDriver. So the
acceptance scenario is written **once** against a tiny `Driver` interface
(`apps/web/e2e/scenario.ts`) and run by two drivers:

- **Playwright driver** — Chromium, Firefox, Playwright WebKit, against both the dev server and
  `vite preview` of the production build.
- **In-page DOM driver** — compiled to one script and evaluated in the Tauri webview by a
  `selftest` cargo feature (never in a normal build). It drives the real UI through the DOM
  (labels, button names, visible text), reports through a `selftest_report` command that only
  the selftest capability grants, and the process exits 0/1. The harness
  (`pnpm test:e2e:desktop`) builds the production bundle, builds the app with the feature, runs
  phase *create*, then **relaunches the process** and runs phase *read back* against the same
  data directory (a temp dir, so it never touches real user data).

What this proves on macOS: the shipped web bundle boots in WKWebView, the Tauri adapters are
selected, migrations apply through rusqlite, a project and blob written through the UI survive a
full process restart and are read back through the UI. What it does not prove: real user input
events (the DOM driver uses `click()`/`input` events, not OS events), and anything on Windows or
Linux.

## Test plan

| Acceptance criterion | How it is proven |
|---|---|
| e2e passes in Chromium / Firefox / WebKit (web) | `pnpm test:e2e`: Playwright, 3 browsers × {dev server, preview of the production build}, the shared scenario + a deep-link reload |
| e2e passes in Tauri on macOS | `pnpm test:e2e:desktop` (selftest build, two process launches) — run on this machine, result recorded below |
| e2e passes in Tauri on Windows / Linux | **Not exercisable here** (macOS-only machine, Q11). `ci.yml` gets a `desktop-e2e` job (Linux: `tauri-driver` + WebKitGTK under xvfb running the same selftest harness; Windows: same harness) kept correct but not run |
| `crossOriginIsolated === true` | asserted in the scenario on web, on both dev and preview servers, in all three browsers |
| platform interfaces behave the same | Vitest contract suite against fake, sqlite-wasm core and Tauri adapter; `cargo test` for the Rust commands and for applying the shared migrations |
| app never imports `@tauri-apps/*` | Biome `noRestrictedImports` override + a Vitest guard |

## Spec gaps found

- **CSP vs. Tauri.** A `<meta>` CSP in `index.html` would also apply inside Tauri and block its
  IPC, so the web CSP is sent as a header (Vite `server`/`preview` headers) and Tauri's comes from
  `tauri.conf.json`. Production hosting must send the same headers — the CDN config does not exist
  yet (01 §9), so the header set is one exported module the future deploy WP can consume.
- **SPA fallback.** `/song/:id` on reload needs index.html fallback from whatever serves the
  bundle; Vite preview does it, a CDN must be configured to.
- To be extended during implementation.

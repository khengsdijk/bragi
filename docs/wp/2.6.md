# WP-2.6 — Planner v1: ops-only plans, explain, lasso & prompt bar

- **Spec refs:** [06 §1–5, §7–9](../../specs/06-ai-planner.md), [07 §4.3, §4.9](../../specs/07-song-canvas.md), [10 §7, §8 check 3](../../specs/10-fusion.md), [ADR-0012](../../specs/decisions/ADR-0012-describe-llm-client.md)
- **Depends on:** 2.3, 2.5 (Done)
- **Size:** L
- **Branch:** `wp/2.6-planner`

## Goal

Free text becomes an `EditPlan`: 1–3 ops-only variants that land in the Audition bar (WP-2.5).
Lasso a region (or select one), type or pick a chip in the prompt bar, get candidates, compare,
accept. "Explain this" answers questions grounded in the analysis. Generation steps are part of the
schema but no generation capability is offered until WP-2.7, so every v1 plan is ops-only.

**Acceptance (12):** planner bench metrics for the ops-only cases (06 §9: valid ≥ 98 % after the
repair round, expectations ≥ 85 %, P50/P95 < 2.5 s / < 6 s, over-reach 0); the prompt-injection
test passes; 10 §8 check 3 passes on the planner path (20 artist-name prompts rewritten to
descriptors with a notice, 20 clean prompts unchanged).

## Decisions

- **The request carries the document.** 06 §2 has the API load the commit snapshot, but the server
  holds no projects (history is local-first, WP-2.1; hosted sync is deferred by the owner). v1
  `PlanRequest` carries `doc` (the `Project` at `commitId`) and the API never stores it. Recorded
  as a deviation and a note in 06 §2. Analyses travel inside the doc (`analysis` refs and
  effects), which is everything `summarize_for_llm` needs.
- **The API runs the model in Node** with the existing `@bragi/model-wasm` build (`initSync` with
  the `.wasm` bytes), for `summarize_for_llm` and the dry-run.
- **LLM client in TypeScript, no SDK** (ADR-0012 applies as written: OpenRouter chat completions
  with `fetch`, injectable transport, `HTTP-Referer`/`X-Title`, `provider.data_collection: "deny"`
  by default, the same error mapping). Tool calling with one tool `propose_edit_plan`; a plain
  JSON reply is accepted and validated the same way.
- **Tiers in `config/planner.toml`** (`fast`, `smart`, `explain`; OpenRouter slugs; default
  `deepseek/deepseek-v4.1-flash` for `fast`/`explain` and a stronger tool-calling model for
  `smart`, checked on OpenRouter's model list when the task lands). `BRAGI_PLANNER_MODEL_FAST` /
  `_SMART` / `_EXPLAIN` override.
- **Artist names:** a deterministic pre-pass finds names from a curated list (+ the library
  metadata the request supplies) and replaces them with descriptors from a small curated map
  before the LLM sees the prompt; the plan carries `notices: ["I described \"…\" as …"]`. The
  system prompt also forbids names; a post-check rejects any name left in a generation prompt.
- **Region discipline** (06 §7) is a validator over the dry-run's touched ticks and tracks, not
  a prompt rule only. A variant with `scope: "song"` passes only when the song-wide classifier
  fired on the prompt.

## Approach

### A. `summarize_for_llm` + WASM (Rust)

- `crates/bragi-model/src/summary.rs`: `summarize_for_llm(doc, focus) -> String` in the 06 §2
  format (song line, tracks, sections table with bars/startBar/energy/chords/active stems/locked,
  focus region with that track's fx and descriptors, current fx/macros). Deterministic, ~2–6k
  tokens for a 4-minute song; values come from the analysis effects in the doc; missing analyses
  are omitted, never invented. User-controlled strings (titles, names, lyrics) are escaped and
  quoted as data (06 §7 injection rule). Snapshot tests (insta) on the fixtures.
- WASM export `summarizeForLlm(handle, focusJson)`, regenerated package, README updated.

### B. Planner service (TS, `services/api/src/planner/` + `packages/schemas/planner/`)

- Schemas first: `plan-request`, `edit-plan` (with `PlanStep` incl. `generate`/`apply_generated`/
  `smooth` as in 06 §3, `scope?: "song"` on a variant, `notices`), `explanation`; regenerate.
- `catalogue.ts`: the capability catalogue generated at build time from
  `crates/bragi-dsp/fx_catalog.json`, `macros.json`, the op schemas, and an empty generation
  registry (WP-2.7 fills it): IDs, param ranges, no prose.
- `openrouter.ts` (client), `config.ts` (`config/planner.toml` + env), `prompts/system.md`
  (versioned, 06 §4 rules), `classify.ts` (tier heuristic, song-wide intent, explain intent),
  `policy.ts` (artist pre-pass + post-check), `validate.ts` (schema → dry-run each variant with
  the model → region discipline → credits, one repair round), `explain.ts`.
- `POST /v1/plans` → `EditPlan` or `Explanation` (`explain: true` or an explain intent). Errors
  use the existing error envelope (`PLANNER_UNAVAILABLE` without a key, `PLAN_INVALID` after the
  repair round, `PROMPT_POLICY`).
- Offline tests with a fake transport: request shape (tool, headers, data policy), tiering,
  repair round, region discipline, injection (instructions in a track name and in lyrics are
  ignored: the fake model echoes them and validation rejects/does not follow them), policy 20+20.

### C. Planner bench (`services/api/test/planner-bench/`)

- ~40 ops-only cases over 2–3 fixture projects with structural expectations (06 §9), a runner
  `pnpm bench:planner` that loads `.env` like `dev:backend`, runs every case against the real
  OpenRouter model, and prints valid rate, expectation pass rate, P50/P95 latency, over-reach and
  cost; writes `bench-results/planner-<date>.json` (git-ignored). A `--dry` mode replays recorded
  replies for an offline smoke test in `pnpm test`.

### D. Client: lasso, prompt bar, plan → audition, explain (TS/React)

- Platform `planner` API (`plan(request)`), web + Tauri hosts.
- Canvas `lasso` tool (`L`, 07 §4.3): bounding region snapped to beats (bars above 2 bars, `Alt`
  disables); keyboard path: the current selection or the whole song.
- Prompt bar anchored to the selection: text field, local suggestion chips by role (07 §4.3),
  pulsing region while waiting, the `interpretation`, notices, a clarification with its options.
- Variants → candidate commits (apply each variant's ops to the base doc) → `openCandidates` in
  the WP-2.5 Audition store; accept commits through history with the variant label.
- Explain mode (07 §4.9): a toggle; clicking a section/point asks for an Explanation; popover
  text + canvas highlights.
- Vitest for the controller; a Playwright test against a fake planner (no key needed) and a live
  one gated on the key.

### E. Verification (Opus)

Bench run with the real key (M2 Pro host, OpenRouter latency), live e2e (lasso → prompt → three
candidates → accept → undo), outcome.

# WP-2.6 — Planner v1: ops-only plans, explain, lasso & prompt bar

- **Spec refs:** [06 §1–5, §7–9](../../specs/06-ai-planner.md), [07 §4.3, §4.9](../../specs/07-song-canvas.md), [10 §7, §8 check 3](../../specs/10-fusion.md), [ADR-0012](../../specs/decisions/ADR-0012-describe-llm-client.md)
- **Depends on:** 2.3, 2.5 (Done)
- **Size:** L
- **Branch:** `wp/2.6-planner`

## Goal

Free text becomes an `EditPlan`: 1–3 ops-only variants that land in the Audition bar (WP-2.5).
Lasso a region (or select one), type or pick a chip in the prompt bar, get candidates, compare,
accept. "Explain this" answers questions grounded in the analysis. Generation steps are part of the
schema but no generation capability is offered until WP-2.7, so every v1 plan is ops-only.

**Acceptance (12):** planner bench metrics for the ops-only cases (06 §9: valid ≥ 98 % after the
repair round, expectations ≥ 85 %, P50/P95 < 2.5 s / < 6 s, over-reach 0); the prompt-injection
test passes; 10 §8 check 3 passes on the planner path (20 artist-name prompts rewritten to
descriptors with a notice, 20 clean prompts unchanged).

## Decisions

- **The request carries the document.** 06 §2 has the API load the commit snapshot, but the server
  holds no projects (history is local-first, WP-2.1; hosted sync is deferred by the owner). v1
  `PlanRequest` carries `doc` (the `Project` at `commitId`) and the API never stores it. Recorded
  as a deviation and a note in 06 §2. Analyses travel inside the doc (`analysis` refs and
  effects), which is everything `summarize_for_llm` needs.
- **The API runs the model in Node** with the existing `@bragi/model-wasm` build (`initSync` with
  the `.wasm` bytes), for `summarize_for_llm` and the dry-run.
- **LLM client in TypeScript, no SDK** (ADR-0012 applies as written: OpenRouter chat completions
  with `fetch`, injectable transport, `HTTP-Referer`/`X-Title`, `provider.data_collection: "deny"`
  by default, the same error mapping). Tool calling with one tool `propose_edit_plan`; a plain
  JSON reply is accepted and validated the same way.
- **Tiers in `config/planner.toml`** (`fast`, `smart`, `explain`; OpenRouter slugs; default
  `deepseek/deepseek-v4.1-flash` for `fast`/`explain` and a stronger tool-calling model for
  `smart`, checked on OpenRouter's model list when the task lands). `BRAGI_PLANNER_MODEL_FAST` /
  `_SMART` / `_EXPLAIN` override.
- **Artist names:** a deterministic pre-pass finds names from a curated list (+ the library
  metadata the request supplies) and replaces them with descriptors from a small curated map
  before the LLM sees the prompt; the plan carries `notices: ["I described \"…\" as …"]`. The
  system prompt also forbids names; a post-check rejects any name left in a generation prompt.
- **Region discipline** (06 §7) is a validator over the dry-run's touched ticks and tracks, not
  a prompt rule only. A variant with `scope: "song"` passes only when the song-wide classifier
  fired on the prompt.

## Approach

### A. `summarize_for_llm` + WASM (Rust)

- `crates/bragi-model/src/summary.rs`: `summarize_for_llm(doc, focus) -> String` in the 06 §2
  format (song line, tracks, sections table with bars/startBar/energy/chords/active stems/locked,
  focus region with that track's fx and descriptors, current fx/macros). Deterministic, ~2–6k
  tokens for a 4-minute song; values come from the analysis effects in the doc; missing analyses
  are omitted, never invented. User-controlled strings (titles, names, lyrics) are escaped and
  quoted as data (06 §7 injection rule). Snapshot tests (insta) on the fixtures.
- WASM export `summarizeForLlm(handle, focusJson)`, regenerated package, README updated.

### B. Planner service (TS, `services/api/src/planner/` + `packages/schemas/planner/`)

- Schemas first: `plan-request`, `edit-plan` (with `PlanStep` incl. `generate`/`apply_generated`/
  `smooth` as in 06 §3, `scope?: "song"` on a variant, `notices`), `explanation`; regenerate.
- `catalogue.ts`: the capability catalogue generated at build time from
  `crates/bragi-dsp/fx_catalog.json`, `macros.json`, the op schemas, and an empty generation
  registry (WP-2.7 fills it): IDs, param ranges, no prose.
- `openrouter.ts` (client), `config.ts` (`config/planner.toml` + env), `prompts/system.md`
  (versioned, 06 §4 rules), `classify.ts` (tier heuristic, song-wide intent, explain intent),
  `policy.ts` (artist pre-pass + post-check), `validate.ts` (schema → dry-run each variant with
  the model → region discipline → credits, one repair round), `explain.ts`.
- `POST /v1/plans` → `EditPlan` or `Explanation` (`explain: true` or an explain intent). Errors
  use the existing error envelope (`PLANNER_UNAVAILABLE` without a key, `PLAN_INVALID` after the
  repair round, `PROMPT_POLICY`).
- Offline tests with a fake transport: request shape (tool, headers, data policy), tiering,
  repair round, region discipline, injection (instructions in a track name and in lyrics are
  ignored: the fake model echoes them and validation rejects/does not follow them), policy 20+20.

### C. Planner bench (`services/api/test/planner-bench/`)

- ~40 ops-only cases over 2–3 fixture projects with structural expectations (06 §9), a runner
  `pnpm bench:planner` that loads `.env` like `dev:backend`, runs every case against the real
  OpenRouter model, and prints valid rate, expectation pass rate, P50/P95 latency, over-reach and
  cost; writes `bench-results/planner-<date>.json` (git-ignored). A `--dry` mode replays recorded
  replies for an offline smoke test in `pnpm test`.

### D. Client: lasso, prompt bar, plan → audition, explain (TS/React)

- Platform `planner` API (`plan(request)`), web + Tauri hosts.
- Canvas `lasso` tool (`L`, 07 §4.3): bounding region snapped to beats (bars above 2 bars, `Alt`
  disables); keyboard path: the current selection or the whole song.
- Prompt bar anchored to the selection: text field, local suggestion chips by role (07 §4.3),
  pulsing region while waiting, the `interpretation`, notices, a clarification with its options.
- Variants → candidate commits (apply each variant's ops to the base doc) → `openCandidates` in
  the WP-2.5 Audition store; accept commits through history with the variant label.
- Explain mode (07 §4.9): a toggle; clicking a section/point asks for an Explanation; popover
  text + canvas highlights.
- Vitest for the controller; a Playwright test against a fake planner (no key needed) and a live
  one gated on the key.

### E. Verification (Opus)

Bench run with the real key (M2 Pro host, OpenRouter latency), live e2e (lasso → prompt → three
candidates → accept → undo), outcome.

## Deviations (task A)

- **Energy, chords, active stems and per-track descriptors are `-`.** The recorded effects
  (`specs/02-song-model.md` §6) carry tempo, sections, separation, tags and description only. Energy,
  chords, per-section stem activity and track descriptors live in the analysis blobs, which
  `bragi-model` never reads (no I/O, 02 §1.6). The summary prints `-` for those columns and omits
  descriptors rather than deriving them from the lanes; no schema change was made.
- **Macro values are not stored.** Applying a macro writes ordinary fx cropped to `macroOwned`
  (03 §6.1), so the summary reports the macro ID on its track (`macro: space`) plus the driven fx
  parameters, not a numeric macro value.
- **Signature and error type.** `summarize_for_llm(doc, focus) -> Result<String, ApplyError>` (not
  the old `analyses`/`Option<Region>` sketch and not `LlmContext`). A stale focus track or section
  is a structured `unknown_track` / `missing_target`. 02 §8 and 06 §2 are updated.
- **Song facts come from `analyses[].summary`**, falling back to `tags` effects when a summary is
  absent; genres/moods are de-duplicated in source-ID order. `CAPABILITIES` is omitted: task B
  generates the catalogue in TypeScript.
- **`CURRENT FX/MACROS`** lists tracks with at least one fx instance or a `macroOwned` instance; the
  master chain is not repeated there (its fx are not per-track).

## Bench results

The bench (`pnpm bench:planner`) runs the real planner over 43 ops-only cases on three synthetic
fixtures. Latency is wall time for the whole `POST /v1/plans` path (all calls, including a repair),
measured on the M2 Pro host; the latency itself is OpenRouter's. Every run used
`deepseek/deepseek-v4.1-flash` (the configured default), concurrency 4, and the committed cases.

| Run | Prompt / config | Valid | Expectations | P50 / P95 | Over-reach | Cost |
|---|---|---|---|---|---|---|
| Baseline | v1 prompt, 4096 max tokens | 69.8 % (30/43) | 23.3 % (10/43) | 26.0 s / 94.6 s | 0 | $0.123 |
| 2 | v2 prompt + arrangement classifier | 72.1 % (31/43) | 55.8 % (24/43) | 22.6 s / 90.6 s | 0 | $0.116 |
| 3 | v2 + 8192 max tokens | 90.7 % (39/43) | 81.4 % (35/43) | 18.7 s / 58.0 s | 0 | $0.102 |
| 4 | v3 + structural scope rule + single-track prompt line | 88.4 % (38/43) | 79.1 % (34/43) | 18.9 s / 65.1 s | 0 | $0.141 |
| 5 | v4 + tool-call parse fallback + fairer transition expectations | 90.7 % (39/43) | 86.0 % (37/43) | 15.6 s / 56.4 s | 0 | $0.104 |
| **Final** | v5 + merged-section transition expectation | **93.0 % (40/43)** | **88.4 % (38/43)** | **20.5 s / 66.4 s** | **0** | **$0.104** |

A full `--dry` replay of the run-5 recordings (42 cases have a reply; the empty one is skipped)
scores 92.9 % valid / 90.5 % expectations with the final expectations, in milliseconds — the live
model, not the replay, is the measured thing.

**What the tuning bought**

- **Region scope in the prompt (v1 → v2).** The model was answering a one-section region with
  track-level fx, which act on the whole song. v2 names the pattern explicitly: add the fx at a
  neutral setting, then automate `fx:<id>/<param>` on the section's lane (lane ticks are
  section-relative), or use section ops. The bench's `timeLimited` expectation went from 1/11
  region cases to 10/11, and expectations rose 23.3 → 55.8 %.
- **Brevity + a variant-agnostic interpretation (v1 → v2).** Descriptions asked for ≤ 20 words;
  `interpretation` is one sentence about the sound and must not mention variants or options. This
  fixed the observed leak where a dropped whole-song variant was still described in the
  interpretation. The alternative — spending the repair round on dropped variants — would add a
  whole model call for every partial plan; with this model's calls at 2–20 s that is the wrong
  trade, so the prompt was changed instead and the bench checks it structurally
  (`interpretationExcludesDropped`). Output tokens did not fall (the model spends more on
  reasoning), but the wording is now true after drops.
- **8192 max tokens (run 2 → 3).** `deepseek/deepseek-v4.1-flash` is a reasoning model: five
  cases returned an empty reply at 4096. A direct probe showed `finish_reason: "error"` with 4007
  completion tokens, all of them reasoning. Doubling the limit removed the empty replies and moved
  valid 72.1 → 90.7 %, expectations 55.8 → 81.4 %, P50 22.6 → 18.7 s. Only `[limits]` changed; the
  model slugs in `config/planner.toml` are untouched.
- **Arrangement intent in the classifier.** "Remove the second verse" is a structural change, and
  the validator requires `scope: "song"`, but the old classifier only recognised "whole song". It
  now also treats section verbs near section nouns (and "two bars longer") as song-wide. The
  arrangement cases went from 2/7 valid to 7/7.
- **Structural scope without a region (run 3 → 4).** A structural or master change now needs
  `scope: "song"` even with no lasso, so the UI can warn; unit-tested. The run-to-run numbers around
  this change are noisy (the provider flips individual JSON replies), so its effect is measured by
  the deterministic validator tests rather than by the aggregate.
- **Robustness (run 4 → 5).** The client now prefers a well-formed tool call when a provider
  returns several, and `parsePlan` falls back to the content field. Together with relaxing
  `onlyOpKinds` for legitimate transition ops (a moved/merged section may get a crossfade), this
  moved expectations 79.1 → 86.0 %.
- **Remaining gaps.** Valid 93.0 % is short of 98 %: the failures are a malformed tool-call JSON,
  an invented schema property and one empty reply, all model/provider behaviour (the raw reply is
  kept in the report). P50/P95 are far above the 2.5 s / 6 s target because the default model emits
  2–4k reasoning tokens per call (10k on a long policy prompt); the task forbids changing the
  default model, so the bench reports the number for the reviewer's model choice.

## Deviations (task B)

1. **`PlanRequest.doc` replaces `projectId`/`commitId`.** 06 §2 has the API load a commit snapshot,
   but the server holds no projects (history is local-first; hosted sync is deferred). The request
   carries the `Project` and the API never stores it; `packages/schemas/planner/plan-request.schema.json`,
   06 §2 and the endpoint follow that shape. A hosted deployment can add the IDs back additively
   without changing the planner internals.
2. **TOML subset instead of a new parser dependency.** `config/planner.toml` is read by a small
   parser in `services/api/src/planner/config.ts` that supports `[section]`, `key = value`, strings,
   integers, floats, booleans and comments. The API's dependency tree has no TOML parser and adding
   one would need an ADR; the parser rejects arrays, inline tables, dates and other constructs with a
   line number rather than guessing. JSON was the alternative; TOML keeps the config readable and
   matches the plan's naming.
3. **The dry run stubs asset metadata.** The request carries no asset index, but `bragi-model` checks
   that every clip's asset exists when an op batch is applied. Validation synthesises an `AssetMeta`
   for every referenced hash with a duration long enough for the clips. The dry run therefore checks
   op structure, region discipline and locks, not media metadata (06 §5 already says generated assets
   are stubbed).
4. **Region discipline uses the canonical document diff.** The before document is read back through
   the model before the ops are applied, so both sides of the diff share the Rust serialiser's field
   order and optional-field normalisation. Structural changes are song-wide, track-level fx/mixer
   changes touch their track, and lane/section changes touch their absolute section span. Locked
   sections are checked separately and always rejected.
5. **The system prompt is read from `prompts/system.md` at runtime.** `tsc` does not copy `.md` files
   into `dist/`, so the loader falls back to `services/api/src/planner/prompts/` (the source tree ships
   in the API image). The plan and explain prompts both carry a `version` header.
6. **`summarizeForLlm` is behind a feature check until task A lands.** The real summariser calls the
   export when present and throws `PLANNER_UNAVAILABLE` with a clear message when the installed wasm
   build lacks it; tests inject a fake `Summarizer`. The live OpenRouter test also only runs with
   `BRAGI_PLANNER_LIVE=1`.

## Deviations (task C)

1. **43 cases, not "about 40", and three fixtures.** The extra cases are the third prompt-injection
   variant, the locked-section mixed region and the sparse whole-song case. Regions are
   section-aligned: the validator attributes a lane change to the whole section span, so a sub-section
   lasso cannot currently express a lane edit (06 §7 documents the pattern; a future validator can
   narrow the span).
2. **`--tier` filters, it does not force.** It keeps the cases the classifier puts in `fast` or
   `smart`, so a run reports that tier's real behaviour; `--model` is the override.
3. **`maxTokens` is 8192.** The bench showed the default model spending the whole 4096 budget on
   reasoning and returning `finish_reason: "error"` with no content. Only `config/planner.toml`'s
   `[limits]` changed; the model slugs did not.
4. **Structural changes require `scope: "song"` without a region.** The validator previously returned
   before the structural check when no region was selected. Requiring the declaration is what lets the
   UI warn; 06 §7 was updated and `validate.test.ts` covers it. It is stricter than the old code, not
   a schema change.
5. **`parsePlan` accepts the content fallback and the OpenRouter client prefers a well-formed tool
   call among several.** Both are robustness to provider shapes seen in the bench; no schema change.
6. **Over-reach is measured from the canonical diff, not from the ops.** The runner dry-runs every
   returned variant and reuses `diffDocuments`, so a variant that slipped through validation would
   fail the run. It has been 0 in every run, so the assertion has not fired.
7. **Cost is `usage.cost` as OpenRouter reports it.** Some calls return `cost: 0` with a non-zero
   `cost_details.upstream_inference_cost`; the runner does not substitute the upstream number, so the
   table is what the API charges, not an estimate.
8. **The runner uses Node's type stripping plus a tiny resolve hook, not `tsx`.** TypeScript imports
   `./foo.js`; `resolve-ts.mjs` maps that to `./foo.ts` for the source tree. `ApiError` and
   `PlannerModelError` were rewritten from parameter properties to explicit fields so strip-only mode
   accepts them. No dependency was added.
9. **Recordings hold all 43 replies (229 KB) rather than a minimal set.** That keeps the whole suite
   replayable offline with `--dry`; the smoke test uses three of them. They contain replies and usage
   only, never headers or the key.
10. **Policy cases are 5 of the 20 check-3 prompts.** Task C asks for 5; the full 20+20 policy suite
    remains in `planner.test.ts`.

## Deviations (task D)

1. **The prompt bar shortcut is `Cmd/Ctrl+Shift+L`, plus `/`.** `Cmd/Ctrl+L` is the browser's
   address bar on web (and cannot be relied on), `Cmd/Ctrl+K` is the command palette and
   `Cmd/Ctrl+Z` undo. `Cmd/Ctrl+Shift+L` has no standard browser or app bind, stays mnemonic for
   the lasso, and `/` opens the same bar as 11 §6.2 already specifies. Both run "Ask AI…" on the
   current selection, or on the whole song with its "Whole song" label.
2. **Lasso snapping lives in the app, not the renderer.** The canvas reports the free shape's
   seconds region; `features/planner/snap.ts` converts through `ticksAtSeconds`/`secondsAtTicks`
   and snaps to beats (bars above two bars, `Alt` off) as a pure function. The renderer stays
   tempo-map-free (07 §9) and the rule is unit-tested without a GPU.
3. **`sectionFeatures` is a bounded optional request field.** Energy, chords and active stems do
   not exist in the model summary (task A's gap), so the client adds them from the analysis view
   it already draws. The server escapes the block and truncates chords/stems; an old request
   without the field still works.
4. **The design package has no `TextField`; the prompt bar uses a labelled native input.** It is
   styled from the same CSS custom properties as the component set, and its label, target,
   suggestions, busy state, clarification and errors are all DOM-accessible (11 §6).
5. **A plan's success keeps the prompt bar open** with its `interpretation`, notices and "n ideas
   ready" while the Audition bar takes over comparison and Accept. Closing it clears the pulsing
   lasso region; the region does not disappear when the request finishes.
6. **The live planner e2e fakes `POST /v1/plans` at the network layer.** It exercises the real
   upload, document, history, audition and undo paths with no key and no credits; the real-model
   bench/live verification stays task E's job. The demo-page spec runs in every browser under
   `pnpm test:e2e` and stops at "ideas need a saved project" because the demo has no version tree.

# WP-0.7 — Backend & worker skeleton

- **Spec refs:** [05](../../specs/05-backend-and-jobs.md) (all), [01 §1, §4, §6, §8](../../specs/01-architecture.md),
  [13](../../specs/13-agent-guide.md)
- **Depends on:** 0.2 (Done — job/event/error envelopes and the generated TS/Python models exist)
- **Size:** L
- **Branch:** `wp/0.7-backend-worker-skeleton`

## Goal

Stand up the whole async spine of Bragi end to end, with one executable proof:

```
HTTP (login · upload · submit)  ──►  NATS JetStream (JOBS)  ──►  Python worker  ──►  NATS (EVENTS)  ──►  WebSocket
        │                                    │                                              │
        └────────────── OpenTelemetry: one trace across all three hops ─────────────────────┘
```

**Acceptance (from [12](../../specs/12-roadmap.md)):** an integration test logs in, uploads a file,
submits an `echo` job, receives `progress` + `completed` over WebSocket, and shows one trace
spanning API → NATS → worker.

### `services/workers/bragi_common` (Python framework)

`config` (pydantic-settings), `logging` (JSON), `telemetry` (OTLP + `traceparent` extraction),
`hashes`, `s3` (content-addressed, hash-verified IO), `cache` (`job_results`), `cancel`
(NATS KV flag), `progress` (≤2/s), `context` (the `ctx` a capability gets), `protocol` (the
`CAPABILITY`/`ParamsModel`/`run` contract), `worker` (the six-step loop of 05 §4.3). Held to
`mypy --strict`; the untyped `asyncpg`/`boto3` edge is isolated to two modules by a mypy override.

The **`echo`** capability lives in `services/workers/analysis` (`bragi_analysis.capabilities.echo`)
and the container entrypoint is `python -m bragi_analysis`: it validates params, reports progress,
checks the cancel flag, downloads inputs (verifying hashes) and uploads a content-addressed manifest.

### Infra (owned by this WP)

`infra/docker-compose.yml` grows **additively**: `api` (both entrypoints), `worker` (CPU), and a
dev-only `jaeger` for the trace UI. Postgres/MinIO/NATS/Mailpit are untouched, and nothing in this
WP ever tears them down.

## Acceptance test

`services/api/test/integration/acceptance.integration.ts` (its own vitest config, so it never runs
inside `pnpm verify`). It:

1. starts/reuses the docker compose infrastructure, then the `api` and `worker` services;
2. logs in with a **magic link read from Mailpit's API** (the GitHub path needs the owner's app, so
   it is implemented but never exercised here);
3. uploads a generated, licence-clean WAV through `presign → PUT → complete`;
4. subscribes over the WebSocket, submits an `echo` job, and asserts `job.progress` + `job.completed`;
5. reads the final state from `GET /jobs/{id}` (the orchestrator persisted it);
6. asserts **one trace** contains both the API's `jobs.publish` and the worker's `jobs.consume`
   span. The spans are collected by an in-test OTLP/HTTP receiver (`test/integration/collector.ts`)
   that decodes both OTLP JSON (JS SDK) and OTLP protobuf (Python SDK), so no external trace store
   is required for the assertion. Jaeger remains available for a human to browse traces.

Commands:

```bash
docker compose -f infra/docker-compose.yml up -d --wait          # shared infra only
pnpm test:integration                                            # compose api + worker
BRAGI_STACK=local pnpm test:integration                          # api/worker as processes
```

`BRAGI_STACK=local` runs the same entrypoints as ordinary processes and exists for machines that
cannot build the images. **This sandbox cannot pull base images from Docker Hub**, so the acceptance
run recorded below used `BRAGI_STACK=local`; the compose path is committed and is the intended one
on a normal machine.

## Deviations from the plan as first written

| Planned | Shipped | Why |
|---|---|---|
| Migrations as `.sql` files | `src/db/migrations.ts` (SQL in TS) | no copy step; the runner is the only reader, so source and `dist` cannot disagree |
| Jaeger query API for the trace assertion | in-test OTLP/HTTP receiver (+ Jaeger kept for humans) | the assertion becomes dependency-free and works with the containers or local processes |
| `@fastify/cookie` | dropped | Better Auth parses the session cookie itself from the raw header |
| Docker Hub base images for `api`/`worker` | `node:24-alpine` / `python:3.12-slim` committed, not exercised here | registry pulls are blocked in this sandbox |
| Worker owns retries | worker caps retries from JetStream's delivery counter | the orchestrator does not yet own the retry count (05 §4.3) — recorded as a follow-up |

## Spec edits made here

- **05 §3:** noted that `stage` comes from the job's capability and `index` from the gateway's
  per-job counter, because the WP-0.2 `JobEvent` envelope carries neither.
- **05 §5:** noted that Better Auth owns `user`/`session`/`account`/`verification`, and that the
  spec's `users(...)` columns are `plan`/`settings` on Better Auth's `user`.
- **13 §9:** added `test:integration` to the command table.

# WP-2.1 — Version tree & history

- **Spec refs:** [02 §7](../../specs/02-song-model.md), [02 §5.4](../../specs/02-song-model.md) (`region.adopt`), [07 §7](../../specs/07-song-canvas.md), [05 §5, §7](../../specs/05-backend-and-jobs.md) (refs naming, local DB), [13](../../specs/13-agent-guide.md)
- **Depends on:** 0.3 (Done), 1.10 (Done for the web flow)
- **Size:** M
- **Branch:** `wp/2.1-version-tree`

## Goal

Every change to a song becomes a commit in a local DAG with a full snapshot. Undo/redo move HEAD,
editing from a non-tip node branches, branches can be named, versions can be starred, and the
history panel shows the tree. `region.adopt` ("Take this part from…") copies a region from another
commit.

**Acceptance (12):** undo restores a deep-equal doc after any op. 1 000 commits load in the
history panel in < 200 ms.

## Approach

### 1. `region.adopt` in `bragi-model` (Rust)

`bragi-model` has no I/O, so the source commit's document is passed in:

- `pub trait CommitDocs { fn get(&self, id: &CommitId) -> Option<&Project>; }` (impl for
  `HashMap<CommitId, Project>` and an empty `NoCommits`).
- `pub fn apply_with(doc, batch, assets, commits: &dyn CommitDocs) -> Result<Project, ApplyError>`;
  `apply` becomes `apply_with(…, &NoCommits)`. A `region.adopt` whose `fromCommit` is not supplied
  fails with a new `ValidationCode::UnknownCommit` (schema enum first if the codes are schema'd).
- Semantics exactly as 02 §5.4: resolve the region in both docs **by absolute ticks**, clear the
  target region (reuse `apply_region_clear`'s internals), copy clips and automation from the
  source region preserving relative positions, into tracks with the same ID (a source track that
  does not exist in the target is skipped), add 10 ms equal-power fades (`CUT_FADE_SECS`) at both
  boundaries. Derived clip IDs use `derived_id` like `section.duplicate` (Q14 rule).
- WASM: `applyBatchWith(handle, batchJson, commitHandlesJson)` where `commitHandlesJson` is
  `{ "cmt_…": <docHandle> }`.
- Tests in `crates/bragi-model/tests/ops.rs` (+ insta snapshot): adopt from an identical commit is
  a no-op on content (apart from fades), adopt replaces exactly the region, fades present,
  unknown commit error, misaligned section boundaries still work by ticks; extend the proptest
  fuzz so random batches containing `region.adopt` from a random earlier doc never panic or
  produce an invalid doc.
- The UI warning "section boundaries don't align" is computed in TS from `sectionSpans` of both
  docs (07 §7), not in the model.

### 2. Local DAG storage (TS, `packages/app/src/features/history/api/`)

Migration `packages/schemas/sqlite/migrations/003_history.sql`:

```sql
commits(id TEXT PK CHECK cmt_, project_id TEXT NOT NULL REFERENCES projects(id),
        parent TEXT NULL,            -- v1 has at most one parent (02 §7)
        batch TEXT NOT NULL,         -- OpBatch JSON
        label TEXT NOT NULL, author_kind TEXT NOT NULL,   -- denormalised for the panel
        snapshot_hash TEXT NOT NULL, state TEXT NOT NULL CHECK (state IN ('committed','candidate','discarded')),
        candidate_group TEXT, device_id TEXT NOT NULL, created_at TEXT NOT NULL,
        seq INTEGER NULL)            -- server seq after sync (WP-2.9)
refs(project_id, name, commit_id, updated_at, PRIMARY KEY(project_id, name))
local_settings(key TEXT PK, value TEXT NOT NULL)   -- deviceId lives here
outbox(commit_id TEXT PK)                           -- 05 §7, filled now, drained by WP-2.9
```

Refs use the 05 §5 names: `head:<deviceId>`, `branch:<name>`, `star:<commitId>`.

`history-repo.ts`: `deviceId(db)` (creates `dev_<ulid>` once), `insertCommit`, `listCommits(projectId)`
(one query, ordered by `created_at, id`), `getRef`/`setRef`/`deleteRef`, `setCommitState`.
**Snapshots**: the canonical JSON (`model.canonicalJson`) bytes go to the BlobCache; their hash is
the commit's `snapshot`. They are stored **uncompressed** for now: documents are < 1 MB and there is
no zstd in the web build yet. 02 §7 and the `Commit` schema description are updated to say so, and
compression is a new open question. `projects.snapshot_hash` keeps mirroring HEAD's snapshot, so
project open (`getProjectSnapshot`) and the existing flow keep working.

### 3. History store (TS, `packages/app/src/features/history/state/history.ts`)

`createHistory({ platform, songStore, model, projectId })` — a Zustand store with
`{ commits: Map, children, head, branches, starred, redo: CommitId[] }`:

- `load()`: reads commits + refs; if the project has none (a pre-2.1 project), creates a root
  commit from the current snapshot (batch: an empty `system` batch labelled "Imported").
- `commit(batch)`: `songStore.apply(batch)` → on success snapshot + `commitId(parents=[head])` →
  insert commit + move `head:<deviceId>` + outbox + mirror `projects.snapshot_hash`, clear redo.
  This is the one path for user edits; the analysis flow uses it too (author `system`).
- `undo()`: HEAD → parent, pushing the old HEAD on the redo stack; `redo()` pops. Checkout loads
  the target snapshot into the Song Store (`songStore.load`) so the engine resyncs. Undo never
  deletes commits.
- `checkout(id)`: moves HEAD, clears redo. A later `commit` from a non-tip node naturally creates
  a sibling = a branch.
- `nameBranch(name, id = head)`, `star(id)` / `unstar(id)` (`star:<id>` refs).
- `adoptRegion(region, fromCommit)`: loads the source snapshot into a temporary handle, builds a
  one-op `region.adopt` batch, applies through `applyBatchWith`, commits, frees the handle.
- Candidate API for WP-2.5: `addCandidates(batches, group)`, `accept(id)`, `discard(group)` —
  implemented with tests, no UI here.
- Keyboard: `Cmd/Ctrl+Z`, `Shift+Cmd/Ctrl+Z` (07 §4) wired in `SongWorkspace`.

**Undo acceptance test:** for every op kind with a fixture batch (reuse the model's test fixtures
or `packages/app` fixtures), `commit(batch)` then `undo()` yields a document deep-equal to the
document before.

### 4. History panel (TS/React, `packages/app/src/features/history/components/`)

- `layoutTree(commits, head)` (pure): assigns each commit a row (topological, newest first) and a
  lane (branch column); collapses consecutive `system`-authored analysis commits into one
  "Analysis" node (expandable). Unit-tested.
- `HistoryPanel`: a virtualised list (only visible rows rendered; no new dependency — fixed row
  height + scroll offset) of nodes with label, author icon (👤 user, ✨ AI, ⚙ system), branch
  name chips, star toggle, faded discarded candidates. Click / Enter checks out. A node's menu:
  "Name this branch", "Star", "Take this part from here…" (enabled with a region selection).
  Accessible: `role="tree"`/`treeitem`, arrow keys, `aria-current` on HEAD; strings in `en.json`.
- Mounted in `SongWorkspace` as a side panel toggled from the transport/top bar.
- **Perf:** a test builds 1 000 synthetic commits and measures `listCommits` + `layoutTree` +
  first render; budget < 200 ms. Measured in Vitest (Node, M2 Pro) and once in Chromium via the
  e2e page; both numbers recorded with the machine.
- **Compare (A/B)** reuses the audition bar, which is WP-2.5: the panel offers multi-select now,
  and the A/B action lands with 2.5.

### 5. Tests

- Rust: region.adopt unit + snapshot + proptest (above).
- Vitest: history-repo (migration applied from the directory, never a hard-coded list),
  history store (commit/undo/redo/checkout/branch/star/candidates/adopt; undo deep-equal for every
  op kind), `layoutTree`, panel render + keyboard, perf.
- E2E (live stack, after merge): upload → mute a stem → undo → redo → open history → check out the
  root → edit (branch appears) → reload (history persists). axe on the open panel.

## Outcome

Landed 2026-10-19. Everything below was run on an **Apple M2 Pro (macOS)**, not the reference
machine.

**Acceptance (12):**

- *Undo restores a deep-equal document after any op:* automated for all 28 user op kinds in
  `history.test.ts` ("undo restores the document for every op kind"); `analysis.apply` is covered
  by the flow test. Live: the e2e mutes a stem, undoes with `Cmd+Z` and compares the whole
  document (deep-equal), then redoes with `Shift+Cmd+Z`.
- *1 000 commits load in the history panel in < 200 ms:* `history-panel-perf.test.tsx`, Vitest +
  jsdom on the M2 Pro: `listCommits` 4.4 ms, `layoutTree` 1.5 ms, first render 122.2 ms, **total
  128.1 ms** (20 lanes, 1 000 rows; only visible rows are in the DOM). **Not measured in a real
  browser:** the plan's Chromium measurement was not done; jsdom does no layout, so the
  browser number is likely lower for render and is PENDING.

**Live e2e** (`apps/web/e2e/history-flow.spec.ts`, real stack, single-user `dev:backend`):
upload → mute a stem → undo (deep-equal) → redo → open Version history (axe: no serious or
critical issues) → go back to the first version with the keyboard (End, ArrowRight to expand
the Analysis row, End, Enter) → edit there, which branches (the first version gets a second child)
→ reload: the tree, HEAD and the edit persist, and nothing is replayed → axe again. Passes in
**Chromium, Firefox and WebKit** (Playwright, `*-dev`), together with `upload-flow.spec.ts` (warm
cache, three Chromium runs and one each in Firefox and WebKit, all green; one cold Chromium run:
file chosen → playing 5.0 s, stems in the document 42.6 s). `pnpm test:e2e:flow` now runs both
specs.

**`pnpm verify`:** green on the branch before the live fixes; rerun green before the merge.

**Bugs found and fixed while landing it:**

- `region.clear` kept the content *inside* the region; 02 §5.4 says it removes it (task A).
- Overlapping history operations (two quick edits, or an analysis stage during an edit) took the
  same parent and snapshotted each other's changes: all history operations now run through one
  queue (regression test).
- Reopening a song whose HEAD is a version from before some analysis stages replayed those stages
  as new commits on that branch: `resume` now treats a stage as done when any version applied it.
- The engine controller's full reload is async; a delta committed during one (a solo while an
  analysis stage resyncs) was overwritten by the older document. Reloads now end on the newest
  document. This was an intermittent upload-flow failure on warm runs; it predates WP-2.1.
- The history tree element had no box (rows were positioned in a zero-height wrapper).

**Added beyond the plan (for 2.2 and 2.3):** the Song Store's preview layer
(`beginPreview`, `SongState.preview`) and `startGesture`/`coalesceBatches`, so a drag or slider
previews on a copy of the document and commits once (01 §5). 03 §5.3 now describes this instead of
the `PreviewPatch` shadow plan.

**PENDING / open:**

## Deviations (task D)

- `History` gained `readSnapshot(id)`, a read-only snapshot lookup. The panel needs the source
  document for `regionBoundariesAlign` (07 §7) and the store is the only object that owns the
  platform and the snapshot hashes. It does not change any history semantics and is not queued
  (it reads, never writes).
- The plan's "Take this part from here…" is enabled only for `selection.kind === "region"`. The
  canvas selection is one shape at a time (07 §5), so there is no section-span-to-region
  conversion in this task; a sections selection leaves the item disabled.
- `aria-level` is 1 for every version row because lanes are a visual branch column, not a nesting
  level; an expanded analysis run's stage rows are level 2 under their summary. The summary keeps
  `aria-current` so HEAD is announced once when the run is open.
- Compare is the minimal placeholder the plan asks for: Space, Shift/Cmd-click or Ctrl-click
  selects up to two rows, and the disabled "Compare (A/B)" button says "Arrives with the audition
  bar". The action itself is WP-2.5.

## Deviations (task C)

- The upload flow's ingest batch is applied by the Song Store *before* the project row exists (the
  row needs the source the ingest creates), so the history records it with `recordRoot(batch)`:
  the same snapshot/insert/HEAD path as `commit`, without applying the batch a second time.
  `commit(batch)` remains the one path for every later edit; `recordRoot` exists only for the
  already-applied ingest (and the `Imported` root of a pre-2.1 project).
- `SongStore.checkout` returns the same outcome shape as `apply`, with `commit.batch = null`
  because a checkout runs no ops; the engine still follows `commit.delta`.
- Commits written in one clock tick get strictly increasing `created_at` values, so `listCommits`'
  `(created_at, id)` order is insertion order even when the app passes a fixed clock (tests) or the
  clock is coarse.
- The `Imported` root the plan asks for is an **empty** `system` batch, but `op-batch.schema.json`
  requires `ops` with `minItems: 1`. The store therefore writes the empty batch the plan specifies
  (`ops: []`) and the schema is left alone. This is a real spec gap: WP-2.9 pushes commits to the
  server, whose schema validation would reject an empty batch. Either the root gets a schema-valid
  no-op op (e.g. `project.set_meta` with the current title) or `op-batch.schema.json` relaxes
  `minItems` for the root; both are out of task C's scope. Root batch id is the deterministic
  `bat_imported` so two racing `load()` calls make one root, not two.

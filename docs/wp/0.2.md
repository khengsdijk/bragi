## Goal

Make the JSON Schemas in `packages/schemas` the single source of truth for every cross-language
contract, and generate from them TypeScript types and Ajv validators, Rust types (typify, into
`bragi-model`) and Pydantic v2 models (into `bragi_common`). WP-0.3 (ops, validate) and WP-0.7
(backend, workers) build directly on the generated types.

**Acceptance (from [12](../../specs/12-roadmap.md)):**
1. The example document in [02 §10](../../specs/02-song-model.md) validates in TS, Rust and Python.
2. JSON → typed → JSON is lossless in all three.
3. (Scope) `pnpm schemas:gen`, plus a check that generated code is up to date, run inside
   `pnpm verify` and mirrored in the dormant `.github/workflows/ci.yml`.

## Approach

### Schema layout (source of truth)

```
packages/schemas/
├─ song/        common.schema.json ($defs: IDs, AssetHash, ISODate, HexColor, enums, Provenance …)
│               project.schema.json  op.schema.json  op-batch.schema.json  commit.schema.json
│               refs.schema.json  asset-meta.schema.json  region.schema.json …
│  └─ ops/      <op>.schema.json — one file per v1 op (02 §4.2), e.g. track.add.schema.json
├─ analysis/    one schema per stage result blob (04 §3–§7) + section-summary
├─ jobs/        job-request.schema.json  job-event.schema.json (05 §4.2)
├─ api/         errors.json (the stable code registry, 05 §2) + error.schema.json (the envelope)
├─ examples/    one valid instance per root type, used by the tests in all three languages
├─ codegen/     gen.mjs (the pipeline) + rust/ (a tiny typify driver binary)
└─ generated/   bundle.schema.json — every schema merged into one 2020-12 document
```

Conventions, enforced by the bundler so the three generators name things identically:
- every file has a PascalCase `title` (its type name); shared types live in `$defs` with
  globally unique names;
- no anonymous object or multi-value enum schemas inline — they must be a file root or a `$def`
  (single-value enums are allowed inline: they are discriminators like `"op": "track.add"`);
- `additionalProperties: false` on every document object, so an unknown field is *rejected*
  rather than silently dropped by a typed language — which is what keeps round trips lossless;
- `enum: [x]` instead of `const` (typify only enforces the former);
- optional arrays/maps are named `$defs` (typify would otherwise turn `"fx": []` into an absent
  field — lossy);
- ISO dates are a UTC `…Z` string *pattern*, not `format: date-time`, so no language parses them
  into a date type that re-formats them (lossy, and needs `chrono` in the WASM build);
- patterns use `[0-9]`, never `\d` (Rust and Python treat `\d` as Unicode digits), and no
  look-around (Rust `regex`/`regress` and Python must all accept them).

### Pipeline (`pnpm schemas:gen`, `pnpm schemas:check`)

`packages/schemas/codegen/gen.mjs`:
1. **Bundle** every `*.schema.json` into `generated/bundle.schema.json` (refs rewritten to
   `#/$defs/<Title>`), checking the conventions above.
2. **TS types** — `json-schema-to-typescript` → `packages/schemas/src/generated/types.ts`.
3. **TS validators** — Ajv (2020-12) *standalone* code → `src/generated/validators.js` (+ `.d.ts`).
   Precompiled because the UI runs under a strict CSP (01 §10) and runtime Ajv compiles with
   `new Function`.
4. **Rust** — `cargo run -p bragi-schemas-codegen` (typify 0.8 driver) → rustfmt →
   `crates/bragi-model/src/generated/mod.rs`.
5. **Python** — `datamodel-code-generator` (Pydantic v2) →
   `services/workers/bragi_common/src/bragi_common/generated/models.py`.

Every generated file starts with a header naming the source and the command. `--check` produces
all outputs in memory and fails, listing the stale files, if any differs from what is committed.
`pnpm schemas:check` runs first in `pnpm verify` and as a step in `ci.yml`.

## Test plan

| Criterion | Proof (TS · Rust · Python) |
|---|---|
| 02 §10 example validates | `fixtures/projects/example-02-10.json` validates with the Ajv `Project` validator · deserializes into `bragi_model::generated::Project` · `Project.model_validate_json` |
| The fixture *is* the 02 §10 example | TS test extracts the JSON block from `specs/02-song-model.md` §10 and deep-equals the fixture |
| Lossless round trip | parse → typed → serialize → parse, compared as JSON values (numbers numerically, bool ≠ number, key order ignored) to the input, and serializing twice is byte-identical. Run on the fixture **and on one example per root type** (`examples/*.json`, incl. an op batch containing every v1 op) |
| Invalid documents rejected | `fixtures/projects/invalid-cases.json`: mutations of the valid example (unknown field, bad hash, bad enum, missing required, wrong discriminator, wrong `schemaVersion`, …), each rejected in all three languages; numeric-range cases rejected by Ajv and Pydantic (typify does not check ranges — that is `validate`'s job in WP-0.3, stated in the case file) |
| Every root type covered | each language's test asserts its list of root types equals the set of `examples/*.json` |
| Generated code is fresh | `pnpm schemas:check` (in `verify`) + a Vitest test of the bundler's convention checks |
| Error code registry = envelope enum | TS test: `api/errors.json` codes equal the `ErrorCode` enum |

## Spec gaps found (resolved here unless noted)

| Gap | Resolution |
|---|---|
| 02 §10 is abridged (`"prj_01JAB3..."`, `"sha256:9f2c..."`), so it cannot validate against real ID/hash patterns | Spec example completed with full-length IDs and hashes; the fixture equals it (tested) |
| 02 §2.1: example IDs (`trk_mix`, `sec_01`) are not ULIDs | Schema checks prefix + `[0-9A-Za-z]`; ULID is a *generation* rule. Clarified in 02 §2.1 |
| ID prefixes for jobs, plans, macros, users are undefined | `job_` (already used in 05 §3), `pln_`, `mac_`; user IDs are opaque strings (Better Auth owns them). Added to 02 §2.1 |
| `ISODate` format undefined | RFC 3339 in UTC with `Z`. 02 §2.2 |
| Op envelope shape undefined (02 §4.2 lists payloads only) | `{ "op": "<name>", …payload }`. 02 §4.1 |
| `CurvePoint` (02 §3.5), fx/automation `scope` (02 §4.2) undefined | Defined in the schema, documented in 02 |
| 02 §6 names stages `energy`, `tags`, `embeddings`, `description`; 04 and 05 §4.1 use `loudness_energy`, `tag`, `embed_full`, `describe` … | `AnalysisStage` = the 04/05 stage names; 02 §6 wording aligned |
| `analysis.apply` `effects[]` undefined | Typed as an array of free-form objects; → open question for WP-1.8 |
| `meta.suggestedSections` (02 §6) has no shape | Left out of the schema; → open question for WP-1.8 |
| `section.duplicate`/`split`, `clip.split`: IDs of copied/split *clips* are not in the payload, so `apply` cannot be deterministic | → open question for WP-0.3 |
| 01 §7 "every schema carries a `schemaVersion`" vs 05 §4.2 envelopes without one | Top-level documents (project, analysis blobs, job envelopes) carry `schemaVersion: 1`; ops/batches/commits are versioned by the project they apply to. 05 §4.2 and 01 §7 updated |
| Analysis blob shapes in 04 are prose | Schemas derived from 04 §3–§7; shapes 04 leaves open (loudness series, embeddings blob) recorded as an open question for WP-1.2 |
| API error codes are not listed anywhere but `api/errors.json`, which did not exist | Initial registry derived from 02/04/05 |
| Canonical number formatting: Rust/Python re-emit `0` as `0.0` for float fields | "Lossless" = equal as JSON values; canonical bytes are `canonical_json`'s job → open question for WP-0.3 |

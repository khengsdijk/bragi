## Goal

One capability, `analysis.describe`, on the WP-0.7 worker framework. It turns the analysis blobs
(structure, energy, harmony, rhythm, tags, stem activity) into a structured prompt, asks Claude for
the `DescriptionResult` (04 §6.3), and runs a **grounding post-check** that removes any claim the
analysis does not support, in particular instruments that are absent from the tags and stems.

**Acceptance (from [12](../../specs/12-roadmap.md)):**
1. 0 hard failures on the eval checklist (04 §6.3 / §8).
2. The grounding post-check rejects injected hallucinated instruments (unit test).

## Environment constraints (stated up front)

- macOS arm64, CPU only. **No `ANTHROPIC_API_KEY` in this environment** (13 §1.7, secrets never in the
  repo). Every test runs against a **fake Claude client**; the one real-API smoke test is skipped
  unless the key is set.
- **No eval set** (`fixtures/eval/manifest.json` lists no tracks, Q32). The checklist runs over
  synthetic analysis fixtures and canned model replies. That proves the checklist machinery and the
  post-check, **not** the quality of real Claude output. Criterion 1 is therefore reported
  **PENDING**, never as a pass on real data.
- No audio is needed: `describe` consumes blobs only, so no ffmpeg and no audio fixtures.

## Approach

### Contracts

`DescriptionResult` (`packages/schemas/analysis/description.schema.json`) already exists and fits
04 §6.3 (`summary`, `sectionNotes[]`, `whatMakesItWorks[]`, optional `suggestedTitle`). No schema
change is planned. If one turns out to be needed (for example a `grounding` report), it goes
schema-first and is regenerated, and the change is recorded here.

### Decision: the official `anthropic` Python SDK (ADR-0012)

04 §6.3 says "Claude via the API". The repo has no Claude client yet. The official Python SDK
(`anthropic`, MIT) is the default per the skill's rule, and the brief names it. Its transitive
dependencies are recorded in ADR-0012 with their licences. It is added to `bragi-analysis` only (not
to `bragi_common`), and is imported lazily so the module tree stays importable without a key.

### Model tiering

The model ID is **not** hard-coded in code. It comes from `config/describe.toml` (`model`), can be
overridden with `BRAGI_DESCRIBE_MODEL`, and can be overridden per job with the params field
`model`. The default is `claude-sonnet-5-5`, as the brief requests for this tier (06 §4 leaves the
ID to config). The spec fixes no ID for `describe`.

### Module layout (`services/workers/analysis/src/bragi_analysis/`)

```
describe/
  features.py    blobs -> DescribeFeatures (section records §5.6, energy shape, key/bpm, tag labels, stems)
  prompt.py      SYSTEM_PROMPT (versioned constant), user-message builder (features as data, delimited)
  llm.py         DescribeClient protocol; AnthropicClient (lazy `anthropic` import, no key logging)
  grounding.py   post-check: instrument/key/bpm/section-index grounding; strips unsupported sentences
  checklist.py   automated 04 §6.3/§8 checklist (hard vs soft findings)
  pipeline.py    build prompt -> call -> parse JSON -> schema-validate -> ground -> DescriptionResult
capabilities/describe.py
config/describe.toml
```

`features.py`, `grounding.py`, `checklist.py` and `prompt.py` are pure and need no I/O, so they are
unit-tested directly. The capability does the blob downloads and the client construction.

### Feature input (what Claude sees)

Only derived features and controlled-vocabulary labels: no audio, no lyrics, no file names and no
artist or title metadata. Sections are the §5.6 join of `structure`, `loudness_energy.sections`,
`harmony.sections` and `stem_activity.presence`. Tags are the top-k labels from `tag`. The user
message wraps the features in a delimited `<analysis>` block, which the system prompt marks as data.

### Grounding post-check (04 §6.3, criterion 2)

The "supported vocabulary" for a song is built from the features only:
- instruments: `tag.instruments` labels, plus the instruments implied by the active stem roles
  (`drums`, `bass`, `vocals`, `guitar`, `piano`, `synth`, `strings`);
- key and tempo: `harmony.key` and `rhythm.bpm`.

Each description sentence is scanned for instrument words through a fixed synonym table (for
example `kick`, `hi-hat` and `snare` imply drums; `rhodes`, `keys` and `organ` imply piano or synth).
A sentence that names an instrument outside the supported set is **stripped**. A `sectionNotes` entry
or `whatMakesItWorks` item with an unsupported claim is dropped. Claims of key or tempo that contradict
the analysis are also stripped. Invalid section indices are dropped. If the summary loses every
sentence, the whole result is **rejected** (`GroundingRejectedError`). The report lists what was removed
(counts and labels only, never the prompt or the text, see Logging).

### Eval checklist (automated, 04 §6.3 and §8)

Hard findings (any one fails the track): the output is not schema-valid; the summary is empty;
a section index is unknown; an instrument claim is unsupported after the post-check; a jargon token
survives (`BPM`, `LUFS`, `dBFS`, `RMS`, `spectral`, `centroid`, `z-score`, `sigmoid`, `Roman numeral`,
`MIDI`, `tonic`); an artist name from the blocklist appears. The blocklist is empty in v1 and filled
from the 10 §7 curated list (Q74). Soft findings: summary too long, too many sentences.

### Errors and failure handling (04 §10)

- No API key or the `anthropic` package missing: a clear permanent error, so the stage fails with
  a user-facing reason. It is never silently replaced by fake text.
- Transient API errors: left to the SDK's retries, then surfaced to the framework's retry policy.
- JSON that does not validate: one repair retry with the validation error message, then failure.
- Grounding rejection: the stage completes with no description and `lowConfidence` is not added (the
  blob has no such field). The rejection is logged at warning level with counts only. Recorded as Q72.

### Logging (13 §3)

Info level logs only counts, durations, the model ID and the job ID. Prompts, model replies, summaries
and lyrics are never logged above debug, and debug is off by default. The API key is never logged or
echoed in errors.

## Outcome

API key).** Verified on macOS 15 / arm64 only (Q11).

### What shipped

- `bragi_analysis/describe/features.py` — the 04 §5.6 section join over `structure`,
  `loudness_energy.sections`, `harmony.sections` and `stem_activity.presence`, plus the song-level
  energy shape, key/tempo, top-k labels, active stems and low-confidence/missing stage lists.
  Missing blobs degrade to empty fields; nothing reads audio.
- `prompt.py` — the versioned `SYSTEM_PROMPT` (`describe-v1`) and the `<analysis>`-delimited user
  message. Only derived features reach the model: no audio, lyrics, file names, artist or title.
- `llm.py` — the `DescribeClient` protocol and `AnthropicClient`, with the `anthropic` SDK behind a
  lazy import. A missing key or SDK raises `DescribeUnavailableError`; the key is never logged or
  echoed.
- `pipeline.py` — build prompt → call → parse/validate the `DescriptionResult` → one repair retry
  for malformed JSON → grounding post-check. A volunteered `suggestedTitle` is dropped.
- `grounding.py` — the deterministic post-check (04 §6.3). It strips sentences, list items and
  section notes that name an unsupported instrument family, contradict the key/tempo, hit a
  blocked term or use an unknown section index; it rejects the result when the summary is left
  empty. The instrument table covers the taxonomy ids and the stem roles, normalising
  `electric-guitar` → `electric guitar`.
- `checklist.py` — the automated hard/soft checklist (schema validity, empty summary, unknown
  section, unsupported instrument, jargon, blocked terms; soft length limits).
- `settings.py` + `config/describe.toml` — model/token/blocklist configuration; the model ID is
  overridable per job (`params.model`) and by `BRAGI_DESCRIBE_MODEL`.
- `capabilities/describe.py` + `worker.py` — `analysis.describe` reads only `inputs.blobs`, publishes
  `blobs.describe`, reports progress, honours cancellation and fails clearly (never substitutes
  fake text).
- Tests: `describe_support.py` (fake client, synthetic blobs, fake context) and six
  `test_describe_*.py` files.

### Deviations

1. **Exception names** gained the repo's `*Error` suffix (`GroundingRejectedError`,
   `DescriptionInvalidError`, `ReplyInvalidError`, `DescribeUnavailableError`) for PEP 8 / ruff
   N818, matching `EmbedderUnavailableError`, `TaxonomyError`, etc.
2. **The §5.6 section record also carries `repeatGroup`**, which the spec's record includes and the
   `structure` blob provides.
3. **A reply missing `sectionNotes`/`whatMakesItWorks` defaults them to `[]`** instead of failing
   validation; a missing or empty `summary` still fails the schema (`minLength: 1`). A volunteered
   `suggestedTitle` is dropped before validation.
4. **The grounding instrument table was widened** to cover the taxonomy's instrument labels
   (including `sitar`) and to normalise hyphenated ids. Without this the acceptance hallucination
   would be invisible.
5. `DescribeConfig` uses snake_case Python fields; the TOML keys stay `maxTokens`/`blockedTerms`.
6. 04 §6.3's illustrative output key `whatMakesItWork` was corrected to the schema's existing
   `whatMakesItWorks` (a documentation typo, no schema change).

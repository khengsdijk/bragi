# WP-1.10 — Upload → project → live analysis flow (M1)

- **Spec refs:** [01 §6](../../specs/01-architecture.md), [05 §2–§3](../../specs/05-backend-and-jobs.md)
  (all of 05 for context), [02 §6](../../specs/02-song-model.md) (`analysis.apply`),
  [04 §2–§6](../../specs/04-analysis-pipeline.md), [07 §8](../../specs/07-song-canvas.md),
  [11 §2, §6](../../specs/11-ux-and-accessibility.md), [13](../../specs/13-agent-guide.md)
- **Depends on:** 0.5, 0.7, 1.8, 1.9 (Done) and the 1.2–1.6 workers
- **Size:** M (it is the integration WP, so in practice larger)
- **Branch:** `wp/1.10-upload-live-analysis`

## Goal

Drop a song, watch it become a playable, soloable canvas as the analysis stages land.

```
drop → SHA-256 (Web Worker) → dedupe (BlobCache + POST /assets/presign) → presigned PUT → complete
     → POST /analyses (standard) → orchestrator DAG → Python workers → events.asset.<hash>
     → WebSocket analysis.partial → realtime client → fetch the stage blob
     → effects projection → analysis.apply (Song Store → bragi-model) → canvas + engine
     → stems downloaded lazily into the BlobCache → every instrument soloable
```

**Acceptance (from [12](../../specs/12-roadmap.md)):** the **M1 demo** — dropping a 4-minute fixture
song gives a playable canvas with all stages in <= 60 s (reference GPU), and every stem is soloable.
Works on web and desktop.

**Environment honesty.** This machine is macOS 15 / arm64 with **no CUDA GPU**, no eval set and a
blocked Docker Hub. The 60 s criterion is defined on the reference GPU, so what is measured here
(CPU/MPS, `BRAGI_STACK=local`) is recorded as exactly that and is **not** a pass or a fail of the
criterion. Nothing is estimated.

## Findings in the repo (before writing code)

| # | Finding | Consequence |
|---|---|---|
| 1 | The orchestrator passes `assets.source = <uploaded hash>` to every stage and nothing else (**Q33**). `separation` needs `assets.mix`, `harmony`/`stem_activity`/`stem_embed` need `stem_*` assets, and several stages take optional upstream blobs (`rhythm`, `structure`, `embed_full`, `stem_activity`). Run as-is, `separation` fails and the downstream stages degrade. | A pure **stage-input resolver** (`jobs/stage-inputs.ts`) builds each job's `assets`/`blobs` from the outputs of finished stages, and passes ingest's working asset downstream. Unit-tested without NATS. |
| 2 | Nothing publishes `analysis.partial`: `events.asset.<hash>` has no producer, so the WebSocket topic `asset:<hash>` is silent. | The orchestrator publishes it when a stage completes (and `analysis.failed` when one fails). |
| 3 | Worker outputs (working asset, stems, blobs) are never recorded in `user_assets`, so `GET /assets/{hash}/url` answers `NOT_FOUND` for everything the client needs to download. | The orchestrator records every output hash for the job's user (`role = 'derived'`). |
| 4 | `POST /analyses` re-publishes stages that are already `queued`/`running` when called twice. | Only `pending`/`failed` stages are submitted; the call is idempotent. |
| 5 | The DAG lists stages with no worker yet (`preview`, `energy_stems`, `describe` (WP-1.7), `drum_split`, `transcribe`, `lyrics`). A `standard` analysis would never finish. | `IMPLEMENTED_STAGES` in `jobs/dag.ts`; profiles are filtered by it. WP-1.7 adds `describe`. |
| 6 | A WebSocket subscriber that connects after a stage finished never hears about it (Q25). | Subscribing to `asset:<hash>` replays the finished stages from `analyses` (a snapshot, not an event log). Q25 resolved for analysis. |
| 7 | No `/library` endpoints, no browser API client, no auth UI, no TanStack Query in `packages/app`. | Added (below). TanStack Query is in the 01 §1 stack table, so no ADR. |
| 8 | The local database has only `projects`; a document has nowhere to live between sessions. | Migration `002_library.sql`: `projects.snapshot_hash`, `projects.asset_hash`, `library_items`. Documents are snapshots in the BlobCache. |
| 9 | The web app is cross-origin to the API in dev/preview, and the page is cross-origin isolated (COEP). | Vite proxies `/v1` (HTTP + WebSocket) to the API: same-origin, cookie sessions. MinIO presigned URLs are CORS requests. |
| 10 | `AnalysisRef.summary` (Q26) cannot be written by `analysis.apply` effects, and TS may not edit the document. | Decided after reading `bragi-model`; see "Spec gaps" in the outcome. |
| 11 | 01 §6 step 2 says the project is playable immediately from the original. The `Source` needs `workingAsset` and `durationSamples`, which only ingest produces. | The document is created when `ingest` lands (seconds), not on drop. Until then a plain-language progress state. 01 §6 is amended. |

## Approach

### Backend (`services/api`)

| Piece | Where |
|---|---|
| Stage input wiring (Q33), shared `enqueueReady` for `POST /analyses` and the orchestrator | `src/jobs/stage-inputs.ts`, `orchestrator/handler.ts`, `routes/analyses.ts` |
| `IMPLEMENTED_STAGES`, idempotent submit | `src/jobs/dag.ts`, `routes/analyses.ts` |
| Partial / failure fan-out, derived-asset ownership | `orchestrator/handler.ts` publishes `events.asset.<hash>` |
| Snapshot on subscribe, `analysis.failed` | `ws/gateway.ts`, `ws/messages.ts` |
| `GET /library`, `POST /library/import` | `routes/library.ts` |
| Email-code sign-in + bearer token for clients that cannot receive a cookie from a link (desktop; interim until PKCE, 05 §8) | `auth/auth.ts` |
| CORS for the desktop origin (`CORS_ORIGINS`) | `app.ts` |

### Client

| Package | Piece |
|---|---|
| `packages/api-client` | Typed `fetch` client with a base URL and optional bearer token, and the WebSocket transport (`createRealtime`: `sub`/`unsub`, backoff reconnect, resubscribe, injectable socket). No React, no Zustand. |
| `packages/platform` | `Platform.api` (base URL + credential mode: cookie on web, bearer on desktop); `PickedFile.blob` for zero-copy hashing; the hash worker behind `Hasher`. Desktop needs `dragDropEnabled: false` so the webview delivers DOM `File`s. |
| `packages/app` `features/analysis` | `realtime` (the single client of 13 §3: WebSocket -> TanStack Query cache + Song Store), `stage-effects` (blob -> typed `effects[]`), `analysis-view` (blobs -> `AnalysisView`), the flow controller (hash -> dedupe -> upload -> analyses -> subscribe -> merge), the asset fetcher (lazy stems into the BlobCache) |
| `packages/app` `features/library` | drop zone, library list (local `library_items` + `projects`), upload progress, sign-in form |
| router | `/` is the welcome/library page; `/song/$id` opens the stored snapshot and, if analysis is still running, resubscribes |

State rules (13 §3): Zustand for UI state, TanStack Query for server data, the Song Store for the
document, and **one** `realtime` client that writes to all three. TS never mutates the document:
every merge is an `analysis.apply` batch authored by `system`.

### Stage blob -> document / view

| Stage | Document (`analysis.apply` effects) | `AnalysisView` (not in the document) |
|---|---|---|
| `ingest` | none; creates the doc with the `Source` (working asset, duration) | peaks |
| `rhythm` | `tempo`: beats -> tempo map in ticks (PPQ 960) + time signature | none |
| `structure` | `sections` (verbatim) | none |
| `separation` | `separation` (stems + residual) | none |
| `tag` | `tags` | none |
| `describe` | `description` (when WP-1.7 lands) | none |
| `loudness_energy` | none | `energy` curve |
| `harmony` | none | `chords` |
| `stem_activity` + `rmsDb` + energy | none | ribbon thickness (an approximation; real per-stem RMS/brightness/noisiness curves need `energy_stems` or engine peaks, open question) |

### What landed

**Backend (`services/api`)**

- `jobs/stage-inputs.ts` — the pure stage-input resolver (Q33/finding 1). It
  passes the upload to `ingest`, the **working asset** downstream as both
  `source` and `mix`, attaches `separation`'s stems/residual, and attaches the
  optional blobs (`rhythm`, `structure`, `embed_full`, `stem_activity`). It has a
  `loadStageResults(pool, hash)` helper that reads `analyses.blob_hash` and the
  completed jobs' `outputs`.
- `orchestrator/handler.ts` — every worker output (assets **and** blobs) is
  recorded in `assets` and `user_assets (role = 'derived')` for the job's user
  (finding 3); a finished stage publishes `analysis.partial` on
  `events.asset.<uploadHash>` and a failure publishes `analysis.failed`
  (finding 2); dependents are submitted through the resolver.
- `POST /analyses` is **idempotent** (finding 4): `planAnalyses` treats
  `queued`/`running`/`done` stages as "leave alone", so a reload or retry cannot
  duplicate work, and a completed stage blocks its dependents. The rule is a pure
  function and is unit-tested.
- `IMPLEMENTED_STAGES` gates every profile (finding 5): `preview`,
  `energy_stems`, `describe`, `drum_split`, `transcribe` and `lyrics` are not
  scheduled until their workers exist. There is a `TODO(WP-1.7)` for `describe`.
- WebSocket `asset:<hash>` subscriptions now **replay** the finished and failed
  stages from `analyses` (finding 6 / Q25); the replay is a snapshot and is safe
  to send twice.
- `/v1/library` — `GET` (paged, with per-asset stage statuses), `POST /import`
  (creates `library_items` and enqueues `quick`), `PATCH`, `DELETE`.
- `CORS_ORIGINS` + a Fastify `onRequest` CORS hook, and Better Auth
  `trustedOrigins` extended with the same origins (finding 9, 05 §8).
- No server-side migration was needed: `library_items` already exists. The local
  migration is `packages/schemas/sqlite/migrations/002_library.sql` (finding 8):
  `projects.snapshot_hash`, `projects.asset_hash`, `library_items`; the Rust
  desktop migration list applies the same file.

**Client**

- `packages/api-client` — `createApiClient` (presign/complete/asset-url/
  analyses/library/auth) with the 05 §2 error envelope as `ApiClientError`, and
  `createRealtime`: `sub`/`unsub`, exponential backoff, resubscribe on reconnect,
  injectable socket, and `realtimeUrl`.
- `packages/platform` — `Platform.api { baseUrl, credential }`: the web host is
  same-origin with cookies; the desktop host points at the compute server with
  the bearer mode (see Q81: the bearer token itself is not implemented).
- `packages/app` `features/analysis`:
  - `api/hash.ts` + `hash.worker.ts` — SHA-256 in a worker with a main-thread
    fallback.
  - `api/stage-effects.ts` — result blob → typed `analysis.apply` effects
    (tempo, sections, separation, tags, description), validated against the
    analysis schemas.
  - `api/analysis-view.ts` — `LoudnessEnergyResult` → energy, `HarmonyResult` →
    chords, `StemActivityResult` → ribbons (explicit approximation, Q79),
    `IngestResult.peakPyramid` → `peaks`.
  - `api/document.ts` — the initial document (created when `ingest` lands,
    finding 11) and the `analysis.apply` batch builder.
  - `state/flow.ts` — the flow controller: hash → BlobCache/`presign` dedupe →
    presigned PUT → `complete` → subscribe → `POST /analyses` → snapshot replay →
    merge every stage through the Song Store, download the working asset and the
    stems, persist a snapshot after every stage. Tested against a fake API,
    realtime socket, `fetch` and a real `bragi-model` wasm.
  - `api/host.ts` — builds the API/realtime clients from `Platform.api`.
- `packages/app` `features/library` — `library-repo` (local `projects` with
  snapshots + `library_items`) and the welcome/drop-zone UI: drag-and-drop or
  file picker, plain-language progress, local library list, magic-link sign-in.
- `/song/$id` reopens the stored snapshot in the Song Canvas and rebuilds
  `AnalysisView` from the cached analysis blobs; the canvas is the existing
  WP-1.9 renderer, so mute/solo and playback are the same code path.
- Vite proxies `/v1` (HTTP + WebSocket) to `127.0.0.1:8080`; the page stays
  same-origin, so the session cookie is an ordinary cookie. TanStack Query was
  added (already in 01 §1's stack table; no ADR).

### Deviations and decisions

- **Finding 11 is client-side.** The *document* is created when `ingest` lands,
  in the flow controller, because the document is client state and only
  `bragi-model` may author it. 01 §6 is amended accordingly. The server does not
  build a song document.
- **`describe` is not scheduled** (no worker; WP-1.7 lands separately). The
  effect projection is already implemented, so adding it is one line in
  `IMPLEMENTED_STAGES`.
- **Stems are downloaded eagerly** when separation lands rather than per-ribbon
  (Q80); the engine needs the bytes in the BlobCache to solo.
- **`rhythm` becomes one step tempo point** from the blob's global `bpm`; the
  `tempoCurve` is not used to build a varying map (Q83).
- **No resume after reload** on `/song/$id` (Q82): the snapshot and view render,
  but a still-running analysis is not resubscribed.
- **Desktop auth** is only the `Platform.api` seam; the bearer token/PKCE flow is
  absent (Q81).
- **`POST /library/import` does not create a project** (Q84): it is an asset
  index + quick analysis, and the local project is the document.
- The WP-0.5 Playwright scenario still passes by construction (the projects form
  and `project-id`/`card-status` testids are unchanged; the welcome page adds the
  library above them). The WP-0.5 e2e suite itself was not re-run here.

## Live run (local stack, 2026-10-19)

The integration flow was run against the real backend: docker compose infra (Postgres, MinIO,
NATS, Mailpit) plus the API, the orchestrator and the Python worker as local processes
(`BRAGI_STACK=local`, launched by `scripts/dev-backend.mjs`, the same script as `pnpm dev:backend`).
Separation used the real `htdemucs_6s` weights (fetched with the pinned loader into the gitignored
`.bragi/models`), on **MPS**. There is no `ANTHROPIC_API_KEY`, so `describe` is not faked: it fails
cleanly with `analysis.failed` (`MODEL_ERROR`, "ANTHROPIC_API_KEY is not set"), and the test requires
exactly that. `rhythm` used the weight-free DSP tracker (the `ml` extra and the Beat This! checkpoint
were not installed), and the embeddings are the concept-basis fallback (CLAP weights are pending).

`pnpm test:integration` with `BRAGI_STACK=local`: **2 files, 2 tests passed** (WP-0.7 acceptance and
`analysis-flow.integration.ts`), ~55-58 s end to end including the stack start.
`analysis-flow.integration.ts` checks: magic-link login, upload of the generated 4-minute fixture
(46,080,044 bytes), `POST /v1/analyses` (standard), an `analysis.partial` on `asset:<hash>` for all
11 stages that can run here plus a clean `analysis.failed` for `describe`, every stage blob validated
with the `@bragi/schemas` validators, the working asset, the stems and the residual downloadable
through `GET /v1/assets/{hash}/url`, and a late subscriber receiving the replay snapshot.

### Bugs found and fixed by running it

1. The orchestrator put `assetHash`/`stage`/`profile` into the job's `params`; the workers' strict
   `ParamsModel` rejected them, so **every analysis stage failed**. Orchestration bookkeeping now
   travels in a separate `context` that is stored in `jobs.params` but never published.
2. Every completion re-submitted already queued stages (exponential job fan-out: hundreds of
   duplicate jobs). Only `pending` stages are released, and a queued/failed dependency still blocks
   its dependents.
3. `describe` was submitted with no blobs; it now receives structure, loudness, harmony, rhythm, tag
   and stem activity.
4. A missing `ANTHROPIC_API_KEY` was retried as a transient crash; it is a non-retryable
   `JobFailure`.
5. The WebSocket gateway attached its message listener after the async session lookup, so a `sub`
   sent right at open was dropped and `asset:<hash>` subscribers never got `analysis.partial`. The
   listener is attached first and waits for the lookup.

### Bugs found and fixed by the browser run

1. The flow died at the hand-over (Q82): navigating to `/song/$id` unmounted the drop zone and disposed the flow, so only
   `ingest` reached the document. `StoredSongCanvas` now resumes (`flow.resume`); a failed optional `describe` no longer fails the song.

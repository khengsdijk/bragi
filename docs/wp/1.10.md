## Goal

Drop a song, watch it become a playable, soloable canvas as the analysis stages land.

```
drop → SHA-256 (Web Worker) → dedupe (BlobCache + POST /assets/presign) → presigned PUT → complete
     → POST /analyses (standard) → orchestrator DAG → Python workers → events.asset.<hash>
     → WebSocket analysis.partial → realtime client → fetch the stage blob
     → effects projection → analysis.apply (Song Store → bragi-model) → canvas + engine
     → stems downloaded lazily into the BlobCache → every instrument soloable
```

**Acceptance (from [12](../../specs/12-roadmap.md)):** the **M1 demo** — dropping a 4-minute fixture
song gives a playable canvas with all stages in <= 60 s (reference GPU), and every stem is soloable.
Works on web and desktop.

**Environment honesty.** This machine is macOS 15 / arm64 with **no CUDA GPU**, no eval set and a
blocked Docker Hub. The 60 s criterion is defined on the reference GPU, so what is measured here
(CPU/MPS, `BRAGI_STACK=local`) is recorded as exactly that and is **not** a pass or a fail of the
criterion. Nothing is estimated.

## Findings in the repo (before writing code)

| # | Finding | Consequence |
|---|---|---|
| 1 | The orchestrator passes `assets.source = <uploaded hash>` to every stage and nothing else (**Q33**). `separation` needs `assets.mix`, `harmony`/`stem_activity`/`stem_embed` need `stem_*` assets, and several stages take optional upstream blobs (`rhythm`, `structure`, `embed_full`, `stem_activity`). Run as-is, `separation` fails and the downstream stages degrade. | A pure **stage-input resolver** (`jobs/stage-inputs.ts`) builds each job's `assets`/`blobs` from the outputs of finished stages, and passes ingest's working asset downstream. Unit-tested without NATS. |
| 2 | Nothing publishes `analysis.partial`: `events.asset.<hash>` has no producer, so the WebSocket topic `asset:<hash>` is silent. | The orchestrator publishes it when a stage completes (and `analysis.failed` when one fails). |
| 3 | Worker outputs (working asset, stems, blobs) are never recorded in `user_assets`, so `GET /assets/{hash}/url` answers `NOT_FOUND` for everything the client needs to download. | The orchestrator records every output hash for the job's user (`role = 'derived'`). |
| 4 | `POST /analyses` re-publishes stages that are already `queued`/`running` when called twice. | Only `pending`/`failed` stages are submitted; the call is idempotent. |
| 5 | The DAG lists stages with no worker yet (`preview`, `energy_stems`, `describe` (WP-1.7), `drum_split`, `transcribe`, `lyrics`). A `standard` analysis would never finish. | `IMPLEMENTED_STAGES` in `jobs/dag.ts`; profiles are filtered by it. WP-1.7 adds `describe`. |
| 6 | A WebSocket subscriber that connects after a stage finished never hears about it (Q25). | Subscribing to `asset:<hash>` replays the finished stages from `analyses` (a snapshot, not an event log). Q25 resolved for analysis. |
| 7 | No `/library` endpoints, no browser API client, no auth UI, no TanStack Query in `packages/app`. | Added (below). TanStack Query is in the 01 §1 stack table, so no ADR. |
| 8 | The local database has only `projects`; a document has nowhere to live between sessions. | Migration `002_library.sql`: `projects.snapshot_hash`, `projects.asset_hash`, `library_items`. Documents are snapshots in the BlobCache. |
| 9 | The web app is cross-origin to the API in dev/preview, and the page is cross-origin isolated (COEP). | Vite proxies `/v1` (HTTP + WebSocket) to the API: same-origin, cookie sessions. MinIO presigned URLs are CORS requests. |
| 10 | `AnalysisRef.summary` (Q26) cannot be written by `analysis.apply` effects, and TS may not edit the document. | Decided after reading `bragi-model`; see "Spec gaps" in the outcome. |
| 11 | 01 §6 step 2 says the project is playable immediately from the original. The `Source` needs `workingAsset` and `durationSamples`, which only ingest produces. | The document is created when `ingest` lands (seconds), not on drop. Until then a plain-language progress state. 01 §6 is amended. |

## Approach

### Backend (`services/api`)

| Piece | Where |
|---|---|
| Stage input wiring (Q33), shared `enqueueReady` for `POST /analyses` and the orchestrator | `src/jobs/stage-inputs.ts`, `orchestrator/handler.ts`, `routes/analyses.ts` |
| `IMPLEMENTED_STAGES`, idempotent submit | `src/jobs/dag.ts`, `routes/analyses.ts` |
| Partial / failure fan-out, derived-asset ownership | `orchestrator/handler.ts` publishes `events.asset.<hash>` |
| Snapshot on subscribe, `analysis.failed` | `ws/gateway.ts`, `ws/messages.ts` |
| `GET /library`, `POST /library/import` | `routes/library.ts` |
| Email-code sign-in + bearer token for clients that cannot receive a cookie from a link (desktop; interim until PKCE, 05 §8) | `auth/auth.ts` |
| CORS for the desktop origin (`CORS_ORIGINS`) | `app.ts` |

### Client

| Package | Piece |
|---|---|
| `packages/api-client` | Typed `fetch` client with a base URL and optional bearer token, and the WebSocket transport (`createRealtime`: `sub`/`unsub`, backoff reconnect, resubscribe, injectable socket). No React, no Zustand. |
| `packages/platform` | `Platform.api` (base URL + credential mode: cookie on web, bearer on desktop); `PickedFile.blob` for zero-copy hashing; the hash worker behind `Hasher`. Desktop needs `dragDropEnabled: false` so the webview delivers DOM `File`s. |
| `packages/app` `features/analysis` | `realtime` (the single client of 13 §3: WebSocket -> TanStack Query cache + Song Store), `stage-effects` (blob -> typed `effects[]`), `analysis-view` (blobs -> `AnalysisView`), the flow controller (hash -> dedupe -> upload -> analyses -> subscribe -> merge), the asset fetcher (lazy stems into the BlobCache) |
| `packages/app` `features/library` | drop zone, library list (local `library_items` + `projects`), upload progress, sign-in form |
| router | `/` is the welcome/library page; `/song/$id` opens the stored snapshot and, if analysis is still running, resubscribes |

State rules (13 §3): Zustand for UI state, TanStack Query for server data, the Song Store for the
document, and **one** `realtime` client that writes to all three. TS never mutates the document:
every merge is an `analysis.apply` batch authored by `system`.

### Stage blob -> document / view

| Stage | Document (`analysis.apply` effects) | `AnalysisView` (not in the document) |
|---|---|---|
| `ingest` | none; creates the doc with the `Source` (working asset, duration) | peaks |
| `rhythm` | `tempo`: beats -> tempo map in ticks (PPQ 960) + time signature | none |
| `structure` | `sections` (verbatim) | none |
| `separation` | `separation` (stems + residual) | none |
| `tag` | `tags` | none |
| `describe` | `description` (when WP-1.7 lands) | none |
| `loudness_energy` | none | `energy` curve |
| `harmony` | none | `chords` |
| `stem_activity` + `rmsDb` + energy | none | ribbon thickness (an approximation; real per-stem RMS/brightness/noisiness curves need `energy_stems` or engine peaks, open question) |

| Playwright (`apps/web/e2e/upload-flow.spec.ts`) | against the local stack: sign in -> drop the generated fixture -> progress -> canvas playable -> every stem soloable (one `track.update` batch) -> axe (serious/critical = 0) -> keyboard-only path |
| Desktop | WP-0.5's selftest approach extended with the hash worker + DOM drop path; what cannot be driven from WKWebView (the flow against a live stack) is stated, not implied |

The 4-minute fixture is **generated** (13 §1.7): a deterministic synthesiser (kick/snare/hat, bass,
chord pad, lead) with intro/verse/chorus/bridge/outro dynamics in `scripts/fixture-song.mjs`, shared
by the integration test and Playwright. No audio is committed.

## Measurement plan

Wall clock from "file dropped" to each of: `ingest` landed, first playable canvas, every stage
`done`, every stem downloaded, per stage, on this machine with the stages that run here (CPU DSP
stages; separation on MPS if the `models` group and weights are available). Labelled **not measured
on the reference GPU**.

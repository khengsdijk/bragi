# WP-1.2 — Workers: ingest, rhythm, loudness_energy

- **Spec refs:** [04 §3.1, §5.1, §5.5](../../specs/04-analysis-pipeline.md) (all of 04 for context, §8 eval and §9 `MODELS.md`),
  [05 §4](../../specs/05-backend-and-jobs.md), [13](../../specs/13-agent-guide.md)
- **Depends on:** 0.7 (Done)
- **Size:** M
- **Branch:** `wp/1.2-workers-ingest-rhythm-loudness`

## Goal

Three real `analysis.*` capabilities on the WP-0.7 worker framework, plus the eval harness that
gates them:

1. `ingest` — decode with ffmpeg, produce the 48 kHz / stereo / 24-bit FLAC working asset,
   Chromaprint fingerprint and peak pyramid; reject bad input with the 04 §10 / `errors.json` codes.
2. `rhythm` — beats, downbeats, bpm (folded into 70..180), tempo curve, time signature,
   confidence, `isTempoStable`, `lowConfidence`.
3. `loudness_energy` — EBU R128 (integrated, LRA, true peak, short-term series at hop 0.5 s) and
   the 04 §5.5 energy curve.
4. `fixtures/eval/manifest.json`, `scripts/fetch-eval.sh` and `pnpm eval:analysis`
   (beat F-measure, `reports/analysis-<date>.md`).

**Acceptance (from [12](../../specs/12-roadmap.md)):**
- eval gate for rhythm (beat F >= 0.85) on the eval set;
- ingest rejects corrupt/too-long files with the correct codes;
- the energy curve has the documented hop and range.

## Honest constraints of this environment

- macOS arm64, **no CUDA**: everything runs on CPU (13 §3).
- **There is no eval set.** `fixtures/eval/` is empty and the real ~50 labelled tracks live in an
  owner-provided private bucket that does not exist yet. This WP creates the *machinery*; the F >= 0.85
  gate can only be *run* once the owner supplies the audio. Nothing in this WP fabricates eval numbers.
  The harness is proven on **synthetic** click tracks with known beat times, and those numbers are
  reported as synthetic, never as the gate.
- Model weights are never committed. Tests that need real weights are marked `weights` and skipped
  unless `BRAGI_TEST_WEIGHTS=1`, so `pnpm verify` stays CPU-fast and torch-free.

## Approach

### Layout (all inside `services/workers/analysis`, one module per capability)

```
src/bragi_analysis/
  media/            decode.py (ffprobe/ffmpeg), errors via bragi_common.errors.JobFailure
  dsp/              loudness.py (BS.1770/R128), features.py (flux, centroid), beats.py (DSP tracker)
  capabilities/
    ingest.py  rhythm.py  loudness_energy.py
  rhythm_post.py    beats+downbeats -> RhythmResult fields (shared by every tracker)
  trackers/         base.py (BeatTracker protocol), dsp.py, beat_this.py (torch, optional extra)
  config/energy.toml
  eval/             metrics.py, synthetic.py, harness.py (the `pnpm eval:analysis` entry)
```

### Decisions

| Topic | Decision | Why |
|---|---|---|
| Decode | `ffmpeg`/`ffprobe` subprocesses (spec 04 §3.1) | named by the spec; no Python wrapper dependency |
| Fingerprint | `fpcalc` (Chromaprint, LGPL-2.1) subprocess | named by the spec |
| Loudness | own NumPy/SciPy BS.1770-4 / EBU R128 implementation, cross-checked against ffmpeg `ebur128` and the EBU Tech 3341 sine case | `pyloudnorm` has no LRA / true peak; one small module keeps all four numbers consistent |
| Beat tracker | **Beat This!** (MIT code **and** MIT weights) behind a `BeatTracker` protocol, in an optional `ml` extra (`torch`, `beat-this`); a weight-free DSP tracker (onset flux + tempo autocorrelation + Ellis DP) is the fallback and the test double | 04 §5.1; ADR-0007. Weights stay out of the repo, pinned by hash in `MODELS.md` |
| madmom | **not used** | non-commercial weights (04 §9) |
| Eval metric | `mir_eval.beat.f_measure` (MIT), +-70 ms | 04 §8 |
| Errors | new `bragi_common.errors.JobFailure(code, message, retryable)`; the worker honours `retryable` | the framework today marks every exception retryable, which would retry a corrupt file three times |

### Spec gaps / clarifications found while planning (to be written into the specs)

1. **Energy formula** (04 §5.5): "each feature z-scored, then a sigmoid" is ambiguous. Implemented as
   `sigmoid(sum_i w_i * z_i)` with the weights renormalised over the available features (no
   `active_stem_weight` before separation), and digital silence pinned to 0.
2. **Short-term series alignment**: 04 gives the hop (0.5 s) but not the window position. Value `i` is the
   3 s short-term loudness *centred* on hop `i`'s midpoint, truncated at the file edges, clamped at
   -70 LUFS. Both series have `ceil(durationSec / 0.5)` entries. (Resolves part of Q16.)
3. **Input roles**: `ingest` takes `assets.source`; `rhythm` and `loudness_energy` take `assets.source`
   (the orchestrator today passes the *uploaded* hash to every stage; the working asset is preferred
   when it is passed instead — both decode identically).
4. **Beat This! emits no confidence**: `confidence` is a regularity heuristic (share of inter-beat
   intervals within 10 % of the local median, weighted by beat coverage). Recorded as an approximation.
5. **Peak pyramid shape** (`IngestResult.peakPyramid` is free-form): `{levels:[{samplesPerPeak, peaks:[min,max,...]}]}`
   on the mono mix, two coarse levels.
6. **System binaries**: ffmpeg and chromaprint are OS packages, added to the worker `Dockerfile`.

### Proofs (measured, macOS 15 arm64, CPU)

- Loudness: EBU Tech 3341 997 Hz sine at -23 dBFS reads -23.0 LUFS (+-0.1), true peak -23.0. Against
  `ffmpeg ebur128` on a 4-min noisy click track: I -25.15 vs -25.1 LUFS, LRA 1.17 vs 1.2 LU,
  true peak -1.01 vs -1.0 dBTP.
- Synthetic click suite (7 tracks, **not the gate**): DSP fallback beat F 0.99-1.00 on 4/4 and ramp,
  but downbeat F 0.32 on the 3/4 track (it assumes 4/4). Beat This! `final0` on CPU: mean beat F
  0.984 (0.92 on the 3/4 track), downbeat F 0.41-0.65 (clicks carry no musical cues for bar position).
  This says nothing about real music.
- Speed, 4 min stereo 44.1 kHz WAV: ingest 1.14 s, loudness_energy 2.34 s, rhythm 0.53 s (DSP) /
  5.45 s (Beat This!, CPU). About 9 s total on a laptop CPU, vs the < 15 s `quick` budget (GPU class).
- Tests: 180 Python tests pass (1 skipped: the `BRAGI_TEST_WEIGHTS=1` Beat This! test, which was run
  separately and passed). `pnpm verify` is green.

### Deviations and gaps

- Gate not run (no eval set; Q32). Downbeats and `confidence` for Beat This! are approximations (Q35, ADR-0007).
- Short clips (< ~3 s) get an `exact:` fingerprint because Chromaprint returns nothing.
- Orchestrator still passes the upload hash, not the working asset, to downstream stages (Q33).
- Not exercised: the NATS end-to-end path with the new capabilities (Docker infra not used here), the
  `Dockerfile` ffmpeg / `WITH_ML` layers (unbuilt), anything off macOS arm64 (Q11).
- Spec edits: 04 (v0.3, implementation notes + gate semantics), 12 status row, 13 §9, 15 (Q32-Q36).

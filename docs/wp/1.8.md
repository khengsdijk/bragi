# WP-1.8 — `analysis.apply` + progressive merge

- **Spec refs:** [02 §6](../../specs/02-song-model.md) (all of 02, §6 especially),
  [04 §1–§7](../../specs/04-analysis-pipeline.md), [13](../../specs/13-agent-guide.md)
- **Depends on:** 0.3 (Done)
- **Size:** M
- **Branch:** `wp/1.8-analysis-apply-merge`

## Goal

Implement the `analysis.apply` system op — which WP-0.3 deliberately left unsupported — and the
progressive merge of analysis stages into the song document, so that:

1. every permutation of stage arrival produces the **same** document, and
2. a late `structure` stage on an **edited** document writes `meta.suggestedSections` instead of
   re-splitting.

WP-0.2 typed `effects[]` as free-form objects and left `meta.suggestedSections` out of the schema.
Both shapes are contracts, so they are designed here: **schema first**, then `pnpm schemas:gen`,
then the model.

## Approach

### `analysis.apply` is a reconciler, not a patch

The op payload carries the stage's *projection* — the facts the document needs, typed — and
`bragi-model` derives the arrangement-owned part of the document from **the set of recorded
effects**, not from the incremental sequence of ops. That is what makes the permutation property
provable instead of hopeful:

```
apply(op) =
  record(op.stage, op.blob, op.effects) in analyses[sourceId]
  baseline_prev = build(all effects recorded before)
  baseline_next = build(all effects recorded after)
  if document's arrangement == baseline_prev  →  replace it with baseline_next
  else                                        →  merge additively, never re-split
```

`build` is a pure function of `(sources, recorded effects)`: the tempo map, the section boundaries,
the tracks and the clips. After every op the analysis-owned arrangement equals `build(effects so
far)`, so by induction the final document depends only on the final set — for any order.

`bragi-model` has no I/O and cannot read blobs, so the document must remember the projection it
needs. That is the schema addition in Q12: `AnalysisRef.effects` is the recorded, merged effect
list, and `blob` stays the content-addressed reference to the full result (02 §1.6, "small
documents").

### Deterministic IDs, labels and geometry

- Analysis-owned entities use `derived_id` (WP-0.3, Q14) with the **source ID** as parent, so a
  re-delivery produces the same IDs and never collides with user entities:
  `trk_…` from `derive:<src>/full_mix|stem:<role>|residual`, `sec_…` from
  `derive:<src>/section:<index>`, `clp_…` from `derive:<section>/<track>`.
- Section labels come from the kind plus the number of that kind in the list (`Verse 1`,
  `Verse 2`; `Intro` when the kind occurs once).
- Boundaries: seconds → ticks under the recorded tempo map, then snapped to the **nearest bar**.
  Only the section *starts* are used as boundaries; the last section runs to the end of the
  source. Total length is the source duration rounded up to a whole bar, so nothing is cut off.
- Clips: `srcStart`/`srcEnd` are the section's time span in samples of the 48 kHz working asset,
  clamped to the asset. With a beat grid the clip is `beatgrid`-warped with anchors at the section
  start, every downbeat strictly inside it, and the section end (≥ 2 anchors, always monotonic);
  without one it is `warp: none`.

### Conflict path (edited documents)

"Edited" means `doc.arrangement.sections != baseline_prev.sections` or the timebase differs — i.e.
the user changed the arrangement (split, moved, resized, relabelled, added a section, added a clip,
locked one). Then:

- the arrangement is **never** touched: no re-split, no reorder, no re-time, no lane overwrite;
- `structure` writes `meta.suggestedSections` (Q13) instead, replacing that source's previous
  suggestions; a pristine apply clears them;
- `ingest`/`separation` still add the missing analysis tracks and fill **empty** lanes of the
  existing sections with clips clipped to the source's span, so the song stays playable;
- `tag` merges into `meta.tags`; `describe` sets `meta.description` only when it is absent.

### Q12 — `effects[]`

A list of tagged facts, one per kind, validated against the stage:

| kind | payload | stage |
|---|---|---|
| `tempo` | `tempoMap`, `timeSignatures` | `rhythm` |
| `sections` | `sections` (the `structure` blob's `StructureSection[]`) | `structure` |
| `separation` | `stems` (`StemAsset[]`), `residual` | `separation` |
| `tags` | `genres`, `moods` | `tag` |
| `description` | `description` | `describe` |

Every other stage carries no effects. Effects are stored merged in a fixed kind order, so the
recorded list is a set, not a log.

### Q13 — `meta.suggestedSections`

`SectionSuggestion[]`: `sourceId`, `startSec`/`endSec` (analysis truth), `startTick`/`endTick`
(computed for the canvas), `kind`, `label`, optional `confidence`/`repeatGroup`. `project.set_meta`
gains an optional `suggestedSections` so the UI can accept or dismiss them (an empty list clears).

## Test plan

| Criterion | Proof |
|---|---|
| Permutations agree | `tests/analysis.rs`: exhaustive over all 720 permutations of the six effect-bearing stages, plus a proptest over random effect content and a random arrival order; both compare `canonical_json` with the canonical order |
| Late structure on an edited doc | `tests/analysis.rs`: ingest → rhythm → separation → **user `section.split`** → structure ⇒ sections unchanged, `meta.suggestedSections` has the analysed kinds/ticks, no new section IDs |
| Idempotent re-delivery | the same op applied twice is a no-op in `canonical_json` |
| Effects typing | wrong effect for a stage, duplicate kinds, unsorted/empty structure, duplicate or reserved stem roles ⇒ `analysis_effects` at the op index |
| Geometry | bar snapping, labels/numbering, tick→sample conversion, beatgrid anchors, `warp: none` without rhythm |
| Edited merge keeps the song playable | late separation on an edited doc adds stem tracks and fills empty lanes, never overwrites |
| Op catalogue | `tests/ops.rs`: `analysis.apply` is no longer `unsupported_op`; `region.adopt` still is |

## Dependencies

None. `proptest` and `insta` are already `bragi-model` dev-dependencies; no ADR needed.

## Deferrals

- `AnalysisRef.summary` (Q26) and `AnalysisRef.stems` copy-through is done, but the `summary`
  object needs `key`, which no effect carries.
- Chords/harmony, energy and embeddings do not change the document (02 §6 table) and are not
  effects; they stay blobs.
- Multi-source projects lay their analysis blocks end to end (documented in 02 §6); v1's flow has
  one source.
- Master automation is not re-anchored when a late `rhythm` re-times a pristine document; it is
  empty in the analysis flow (no automation exists yet at that point).
